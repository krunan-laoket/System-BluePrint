# System Blueprint: ชุดเอกสารภาพรวมระบบ

สกิลนี้สร้าง "ชุดเอกสารก่อนเริ่มพัฒนา" ที่บอกว่า **ระบบต้องทำอะไร เพื่อใคร ภายใต้เงื่อนไขอะไร** โดยยังไม่พูดถึงว่าจะ **ทำด้วยเครื่องมืออะไร** เหตุผลคือเอกสารชุดนี้ต้องส่งต่อให้ AI หรือสถาปนิกเลือกเครื่องมือและวางแผนงานภายหลัง ถ้าเอกสารฝังคำตอบด้านเทคโนโลยีไว้ก่อน ผู้เลือกเครื่องมือจะถูกชี้นำโดยไม่มีเหตุผลรองรับ

ผู้อ่านเอกสารมีหลายสายงาน (ผู้บริหาร ฝ่ายบัญชี ฝ่ายกฎหมาย อาจารย์ ทีมพัฒนา) จึงต้องใช้ภาษาธรรมดา ไม่มีโค้ด ไม่มีรหัสที่ต้องตีความ

## หลักที่ห้ามพลาด

1. **ไม่เดา** ข้อมูลทุกอย่างในเอกสารต้องมาจากผู้ใช้ หรือเป็นข้อสมมติที่ติดป้ายชัดและผู้ใช้เห็นแล้ว เพราะเอกสารที่เดาแล้วดูน่าเชื่อถือ อันตรายกว่าเอกสารที่ว่าง คนอ่านจะเชื่อและนำไปตัดสินใจต่อ
2. **ข้อมูลที่ยังไม่ได้ ไม่ปล่อยทิ้ง** เก็บเป็นรายการ "เรื่องที่ต้องตัดสินใจ" (ไฟล์ 13) พร้อมตัวเลือกและผลของแต่ละทาง ให้ทุกคนเห็นว่าอะไรยังค้างและใครต้องตอบ
3. **ถามพร้อมเสนอทางเลือก** ผู้ใช้ส่วนใหญ่ไม่ได้รู้ว่ามีทางเลือกอะไรบ้าง การถามลอยๆ ว่า "ต้องการอะไร" จึงได้คำตอบที่คลุมเครือ ทุกคำถามต้องมีตัวเลือก ผลของแต่ละตัวเลือก และคำแนะนำ
4. **ภาษาคนทั่วไป** ตัวย่อหรือศัพท์เทคนิคที่เลี่ยงไม่ได้ ให้ใส่คำอธิบายสั้นๆ ในวงเล็บครั้งแรกที่ใช้ และรวบรวมลงไฟล์ 14

## ขั้นตอนการทำงาน

### ขั้นที่ 0: ตรวจว่ามีเอกสารเดิมหรือไม่

ถ้าผู้ใช้มีโฟลเดอร์เอกสารชุดนี้อยู่แล้ว (มี `00-readme.md` และ `13-open-decisions.md`) ให้เข้าโหมดอัปเดต: อ่านไฟล์ 13 แล้วถามเฉพาะเรื่องที่ค้าง เมื่อได้คำตอบให้แก้ไฟล์ที่เกี่ยวข้อง ย้ายรายการออกจากไฟล์ 13 (หรือทำเครื่องหมายว่าตัดสินใจแล้วพร้อมวันที่) และปรับ README กับไฟล์ 15 อย่าเริ่มสัมภาษณ์ใหม่ทั้งหมด

### ขั้นที่ 1: เริ่มต้น (ถามไม่เกิน 4 ข้อ)

ถามให้ครบก่อนเข้าหัวข้อหลัก เพราะคำตอบกำหนดว่าจะถามอะไรต่อ

1. ระบบชื่ออะไร และเป็นระบบเกี่ยวกับอะไร (ให้เล่าสั้นๆ 1–3 ประโยค)
2. ใช้ในบริบทไหน: **สถานศึกษา** / **บริษัทเอกชน** / **หน่วยงานราชการหรือรัฐวิสาหกิจ** / อื่นๆ
3. เลือกโหมด: **ฉบับย่อ** หรือ **ฉบับเต็ม** (ดูตารางด้านล่าง)
4. ความซับซ้อนของงาน: เล็ก (คนไม่กี่คน ฟีเจอร์ไม่กี่อย่าง) / กลาง / ใหญ่ (หลายหน่วยงาน หลายระบบเชื่อมกัน) ถ้าผู้ใช้ไม่แน่ใจ ให้ประเมินจากเรื่องที่เล่า แล้วบอกผู้ใช้ว่าประเมินว่าอะไร

หลังได้บริบทแล้ว อ่าน `references/thai-context.md` เพื่อดูหัวข้อที่ต้องเพิ่มหรือเน้นตามบริบท

| | ฉบับย่อ | ฉบับเต็ม |
|---|---|---|
| ไฟล์ที่สร้าง | 00, 01, 02, 03, 04, 06, 08, 09, 13, 14, 15 | ทั้ง 16 ไฟล์ |
| เหมาะกับ | อยากเห็นภาพรวมเร็ว ให้ AI หรือทีมเลือกเครื่องมือต่อ | งานใหญ่ ต้องใช้ประกอบสัญญา TOR หรือรูปเล่ม |

ฉบับย่อยังอัปเกรดเป็นฉบับเต็มได้ภายหลังโดยเรียกสกิลซ้ำ ไฟล์ที่ข้ามให้ระบุใน README ว่า "ยังไม่ได้จัดทำ (ฉบับย่อ)" ในฉบับย่อ ข้อมูลที่ผู้ใช้เล่าเกี่ยวกับข้อมูลที่เก็บ การเชื่อมต่อ และความเสี่ยง (หัวข้อที่ตรงกับไฟล์ 05, 07, 11) ยังต้องไม่ทิ้ง ให้สรุปไว้ในไฟล์ 08 หรือ 15 ตามความเหมาะสม และถามเฉพาะที่กระทบการเลือกเครื่องมือโดยตรง (ข้อมูลส่วนบุคคลมีไหม ต้องต่อระบบอะไร) เพื่อไม่ให้ผู้เลือกเครื่องมือขาดข้อมูลสำคัญ

### ขั้นที่ 2: สัมภาษณ์ทีละหัวข้อ

อ่าน `references/question-bank.md` เพื่อดูคำถาม ตัวเลือก และคำแนะนำของแต่ละหัวข้อ ปรับคำถามให้เข้ากับระบบของผู้ใช้ ไม่ต้องอ่านตามตัวอักษร และข้ามคำถามที่ผู้ใช้ตอบไปแล้วในข้อความก่อนหน้า

**เลือกรูปแบบการถามตามขนาดงาน**

- **รอบที่มีไม่เกิน 4 คำถาม:** ใช้ช่องเลือกคำตอบ (AskUserQuestion) ถ้ามี ใส่ตัวเลือกพร้อมผลของแต่ละทาง
- **รอบที่เกิน 4 คำถาม หรือผู้ใช้บอกว่างานซับซ้อน:** ส่งเป็นข้อความชุดเดียว เรียงเลขข้อ ให้ผู้ใช้ตอบกลับเป็น "1: ... 2: ... 3: ..." โดยไม่ต้องทำเป็นช่องเลือก แต่ละข้อมีรูปแบบนี้

  > **3. ชื่อหัวข้อคำถาม** คำถามสั้นๆ
  > ทำไมถาม: เหตุผลหนึ่งบรรทัด
  > ทางเลือก: (ก) ... (ข) ... (ค) ... พร้อมผลของแต่ละทาง
  > คำแนะนำ: ถ้าเป็นกรณี X ให้เลือก (ข) เพราะ ...
  > ไอเดียเพิ่ม: (ถ้ามี)

- ผู้ใช้สั่งเปลี่ยนวิธีได้ตลอด เช่น "ถามทีละข้อ" หรือ "ส่งมาทีเดียว"

**ผู้ใช้ตอบสั้นๆ ได้ 3 แบบในทุกข้อ**

- "ยังไม่รู้" → บันทึกเป็นเรื่องรอตัดสินใจ (T-xx) พร้อมตัวเลือกที่เคยเสนอ ไม่ถามซ้ำ
- "ตามที่แนะนำ" → ใช้ตัวเลือกที่แนะนำ และติดป้าย [ข้อสมมติ] เพราะเป็นการเลือกตามคำแนะนำ ไม่ใช่ข้อมูลจากผู้ใช้โดยตรง
- "ขอไอเดียเพิ่ม" → เสนอตัวเลือกเพิ่ม 2–3 ทาง พร้อมข้อดีข้อเสีย แล้วถามใหม่

**ตอบกำกวมให้ถามต่อ ไม่ตีความเอง** เช่น ผู้ใช้ตอบว่า "ผู้ใช้เยอะ" ให้ถามว่าประมาณกี่คนต่อวัน และพร้อมกันสูงสุดกี่คน พร้อมยกช่วงตัวเลขให้เลือก (ไม่เกิน 50 / 50–500 / 500–5,000 / มากกว่า 5,000) การให้ช่วงตัวเลขช่วยให้ตอบได้ง่ายกว่าให้ตอบเอง

**ลำดับหัวข้อ** ถามตามนี้ เพราะหัวข้อหลังใช้คำตอบของหัวข้อก่อน (ผู้ใช้ต้องรู้ก่อนจึงจะกำหนดฟีเจอร์ได้ ฟีเจอร์ต้องรู้ก่อนจึงจะวาดขั้นตอนและข้อมูลได้)
เป้าหมายและขอบเขต → ผู้ใช้และสิทธิ์ → ฟีเจอร์ → ขั้นตอนการทำงาน → ข้อมูล → คุณภาพที่ต้องการ → การเชื่อมต่อ → ข้อจำกัดและกฎระเบียบ → หน้าจอ → ความเสี่ยง → เกณฑ์ว่างานเสร็จ

ทุกครั้งที่จบหัวข้อ สรุปสั้นๆ 2–3 บรรทัดว่าบันทึกอะไรไว้ แล้วไปหัวข้อถัดไป ไม่ต้องรอให้ผู้ใช้ตอบรับทุกครั้ง

### ขั้นที่ 3: สรุปให้ผู้ใช้ยืนยันก่อนเขียน

ก่อนสร้างไฟล์ ส่งสรุปสิ่งที่เข้าใจเป็นข้อๆ ในหน้าเดียว แบ่ง 3 กลุ่ม: **ที่ได้จากผู้ใช้**, **ที่ใช้ตามคำแนะนำ (ข้อสมมติ)**, **ที่ยังไม่ได้ (รอตัดสินใจ)** ให้ผู้ใช้แก้ไขได้ เพราะการแก้ตอนยังเป็นสรุปถูกกว่าการแก้ใน 16 ไฟล์ที่อ้างอิงกันอยู่

- `[รอตัดสินใจ]` ยังไม่มีคำตอบ ต้องมีเลข T-xx ชี้ไปที่ไฟล์ 13

### ขั้นที่ 5: ตรวจความสอดคล้องก่อนส่งมอบ

ตรวจแล้วแก้เอง หรือแจ้งผู้ใช้ถ้าต้องตัดสินใจ

- ฟีเจอร์ (F) ทุกตัวมีผู้ใช้ (U) อย่างน้อยหนึ่งบทบาทที่ใช้
- ผู้ใช้ (U) ทุกบทบาทมีฟีเจอร์ที่ทำได้อย่างน้อยหนึ่งอย่าง
- ฟีเจอร์ที่ "จำเป็นมาก" ปรากฏในขั้นตอนการทำงาน (P) อย่างน้อยหนึ่งขั้นตอน
- ข้อมูล (D) ทุกกลุ่มถูกใช้โดยฟีเจอร์หรือขั้นตอนอย่างน้อยหนึ่งอย่าง
- ข้อมูลส่วนบุคคลใน D มีกฎหมายหรือข้อจำกัดที่เกี่ยวข้องใน C
- การเชื่อมต่อ (I) ทุกตัวมีฟีเจอร์ที่ต้องใช้
- ขอบเขตงานไม่ขัดกับงบและเวลา (ฟีเจอร์ "จำเป็นมาก" จำนวนมากเทียบกับงบเล็ก ให้แจ้งเตือน)
- ทุก `[รอตัดสินใจ]` ในไฟล์อื่นมีรายการใน 13 ตรงกัน และทุกรายการใน 13 มีเจ้าของกับกำหนด
- ชื่อเรียกสิ่งเดียวกันตรงกันทั้งชุด (เช่น ไม่ใช้ "ลูกค้า" ในไฟล์หนึ่งและ "สมาชิก" ในอีกไฟล์ ถ้าหมายถึงคนกลุ่มเดียวกัน)

ผลการตรวจสรุปใน README ส่วน "ผลตรวจความครบถ้วน"

### ขั้นที่ 6: ส่งมอบ

- สร้างไฟล์ 00 (README), 14 (ศัพท์) และ 15 (สรุป) เป็นสุดท้าย เพราะต้องดึงข้อมูลจากไฟล์ที่เหลือ
- ส่งมอบไฟล์ให้ผู้ใช้ด้วยวิธีที่สภาพแวดล้อมมี (ส่งไฟล์ หรือบีบเป็น zip ถ้าหลายไฟล์) บอกว่าไฟล์ไหนวางลง Word/PDF ได้ทันที
- แจ้งผู้ใช้สั้นๆ ว่ามีกี่เรื่องที่ค้างอยู่ใน 13 และเรื่องไหนควรตัดสินใจก่อน (เรื่องที่กระทบหลายไฟล์ หรือกระทบงบมากที่สุด)
- ไม่ต้องสรุปทวนเนื้อหาเอกสารซ้ำ ผู้ใช้อ่านได้จากไฟล์

## กติกาการเขียนเอกสาร (ทุกไฟล์)

เพื่อให้วางลง Word/PDF/PowerPoint ได้โดยไม่เพี้ยนและคนต่างสายงานอ่านเข้าใจ

- ใช้หัวข้อ ย่อหน้าสั้น รายการ และตาราง **ตารางไม่เกิน 5 คอลัมน์** ถ้ามีข้อมูลมากกว่านั้นให้แยกเป็นสองตาราง หรือเปลี่ยนเป็นบล็อกต่อรายการ (หัวข้อ+ตารางสองคอลัมน์)
- **ไม่ใช้** โค้ด บล็อกโค้ด Mermaid PlantUML HTML ลิงก์อ้างอิงภายในที่ต้องกดตามถึงจะเข้าใจ หรือสัญลักษณ์ที่ต้องมีเครื่องมือพิเศษถึงจะแสดงผล
- แผนภาพใช้ **ตาราง** ที่บอกว่า "ใคร/อะไร ส่งอะไร ไปที่ไหน" ถ้าต้องวาดลำดับขั้นตอน ใช้รายการเลขข้อพร้อมเงื่อนไข "ถ้า... ไปข้อ..." การวาดกล่องและลูกศรด้วยตัวอักษรมักเพี้ยนเมื่อวางใน Word เพราะฟอนต์ไทยกว้างไม่เท่ากัน
- ไม่ใช้ตัวย่อลอยๆ ถ้าจำเป็น (PDPA, API, SLA) ให้เขียนคำไทยหรือคำอธิบายนำ เช่น "กฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA)" และเพิ่มในไฟล์ 14
- ใช้คำศัพท์ชุดเดียวทั้งชุด ตั้งชื่อให้ตรงกับที่ผู้ใช้เรียกในองค์กรของเขา
- เขียนสิ่งที่ผู้ใช้ตอบด้วยภาษาของผู้ใช้ อย่าเปลี่ยนเป็นศัพท์วิชาการ
- ตัวเลขต้องมีหน่วย และถ้าเป็นเป้าหมายต้องบอกวิธีวัด (เช่น "ลดเวลาทำรายงานจาก 3 วัน เหลือ 1 วัน วัดจากบันทึกของฝ่ายบัญชีรายเดือน")
- **ไม่ระบุยี่ห้อหรือเทคโนโลยีเป็นคำตอบ** (เช่น ภาษาโปรแกรม ฐานข้อมูล คลาวด์) ยกเว้นเป็น **ข้อจำกัดที่ผู้ใช้บังคับมา** เช่น "ต้องใช้ระบบบัญชีเดิมของบริษัท" ให้บันทึกใน 08 พร้อมที่มาของข้อบังคับ
- ข้อกฎหมายที่อ้าง ให้ระบุชื่อกฎหมายและปี และเตือนท้ายไฟล์ 08 ว่าควรตรวจฉบับล่าสุดกับผู้เชี่ยวชาญก่อนใช้ เพราะกฎระเบียบเปลี่ยนได้และสกิลนี้ไม่ใช่คำปรึกษาทางกฎหมาย
