# โครงสร้างมาตรฐานของเอกสารแต่ละไฟล์

โครงเหล่านี้เป็นรูปแบบมาตรฐานที่ฝ่ายธุรกิจและทีมพัฒนาอ่านได้ ปรับหัวข้อย่อยได้ตามระบบจริง **หัวข้อที่ไม่มีเนื้อหาสำหรับระบบนี้ให้ตัดออก ห้ามเว้นหัวข้อว่าง**

วิธีใช้แม่แบบ:
- แม่แบบแต่ละไฟล์อยู่ในกรอบ ```` ````markdown ```` เพื่อแสดงโครงเท่านั้น ในไฟล์จริงให้เขียนเป็น Markdown ปกติ ไม่ต้องมีกรอบ
- ข้อความใน `<...>` คือส่วนที่ต้องแทนด้วยเนื้อหาจริง ห้ามปล่อยค้าง (ตัวตรวจเตือน)
- `{{role}}` เช่น `{{features}}` คือ path จริงของบทบาทนั้นใน `blueprint.json` ต้องแทนทุกจุด รวมในตาราง ผัง และ README (ตัวตรวจแจ้งผิดพลาดถ้าเหลือ) ถ้าบทบาทนั้นไม่มีในโครงการ ให้ตัดส่วนที่อ้างถึงออก ไม่สร้างไฟล์เพิ่มเพื่อให้ครบแม่แบบ
- เลขหัวข้อ `## 1.` ถึง `## 15.` ของไฟล์นี้เป็นเลขของคู่มือ ไม่ใช่เลขไฟล์ ชื่อไฟล์จริงตาม `file-set.md`
- อ่าน `mode` จากทะเบียนก่อน: business ใช้กลุ่มข้อมูลและการกระทำทางธุรกิจ และข้ามแม่แบบเทคนิค (ข้อ 5–7) ส่วน full เพิ่มแบบข้อมูลและสัญญา API ตามที่ออกแบบจริง
- อ่าน `document_style` ด้วย: compact รวมแม่แบบ overview/features และ acceptance/development_plan ตาม file-set.md หัวข้อ 5 ใช้เลขหัวข้อชุดเดียวต่อไฟล์ หน้าจอที่รวมใน scope ให้อ้างหัวข้อใน scope แทนบทบาท screens ที่ไม่มี
- ดูตัวอย่างที่เขียนเสร็จแล้วได้ใน `examples/lab-equipment-loan/` ของสกิล

## สารบัญโครงสร้างไฟล์

1. `{{source}}` — ข้อมูลต้นทางและบันทึกการสัมภาษณ์
2. `{{overview}}` — ภาพรวมโครงการ เป้าหมาย ขอบเขต และการส่งมอบ
3. `{{features}}` — รายการฟีเจอร์และตารางสิทธิ์
4. `{{flows}}` — ลำดับการทำงาน สถานะ และค่าที่ตั้งได้ในระบบ
5. `{{architecture}}` — สถาปัตยกรรมระบบและเป้าหมายด้านคุณภาพ
6. `{{data_model}}` — โครงสร้างข้อมูลและข้อมูลตั้งต้น
7. `{{api}}` — รายการ API และงานตั้งเวลา
8. ไฟล์การเชื่อมต่อภายนอก ฮาร์ดแวร์ ข้อความแจ้งเตือน และกติกาการคำนวณ
9. `{{screens}}` — รายการหน้าจอ
10. `{{decisions}}` — ประเด็นที่ต้องตัดสินใจและบันทึกการตัดสินใจ
11. `{{development_plan}}` — แผนพัฒนาระบบและบริหารความเสี่ยง
12. `{{reports}}` — รายงาน
13. `{{security}}`, `{{migration}}`, และ `{{acceptance}}` (พร้อมเมทริกซ์สอบกลับ)
14. `plans/mockup-plan.md` — ตัวอย่างแผนขั้นถัดไป (โหมด business ที่ยังไม่ทำ Mockup ใช้แผนยืนยันขอบเขตแทน เช่น `plans/scope-confirmation-plan.md` ในตัวอย่าง)
15. `README.md` — ทางเข้าหลัก สถานะเอกสาร และหน้ารับรองฉบับ

## 1. `{{source}}` ข้อมูลต้นทางและบันทึกการสัมภาษณ์

ไฟล์นี้ทำให้ตรวจสอบย้อนกลับได้ว่าเอกสารทั้งชุดมีที่มาอย่างไร ใช้เป็นฐานของการรีวิวในขั้นที่ 5 และใช้เก็บประวัติการสัมภาษณ์กรณีคุยหลายรอบ

````markdown

บันทึกสิ่งที่ได้รับเป็นข้อกำหนดตั้งต้นของระบบนี้ เอกสารอื่นในชุดนี้ตีความและขยายผลจากไฟล์นี้

| รายการ | ค่า |

| ได้รับเมื่อ | <วันที่> |
| ได้รับจาก | <ผู้ใช้ / ลูกค้า / หน่วยงาน ตามที่ผู้ใช้แจ้ง> |
| บริบทองค์กร | <สถานศึกษา / บริษัทเอกชน / หน่วยงานราชการหรือรัฐวิสาหกิจ / อื่นๆ> |
| รูปแบบต้นทาง | <พิมพ์ในแชต / สัมภาษณ์เก็บความต้องการ / ไฟล์ในโฟลเดอร์ ... / รูปภาพ N รูป> |

### ทะเบียนแหล่งข้อมูล

|---|---|---|---|---|
| <ชื่อจริง> | <ตามที่ทราบ หรือไม่ทราบ> | <ตำแหน่งต้นทาง> | <อย่าถือว่ารับรองเพียงเพราะได้รับไฟล์> | <ตามหลักฐานที่มี> |

## 1. สิ่งที่ได้รับจากต้นทาง

<กรณีพิมพ์ในแชต: คัดข้อความของผู้ใช้มาตามเดิม ไม่เรียบเรียงใหม่>
<กรณีโฟลเดอร์ที่อยู่ในโครงการ: ตารางชื่อไฟล์ และสรุปเนื้อหาไฟล์ละ 1–2 บรรทัด ไม่ต้องคัดลอกทั้งไฟล์เพราะต้นฉบับอยู่ในโครงการ>
<กรณีโฟลเดอร์ที่อยู่นอกโครงการ: ตารางชื่อไฟล์ แล้วคัดข้อกำหนดทุกข้อลงมาตามเดิม เพราะต้นฉบับจะไม่ติดไปกับชุดเอกสาร>
<กรณีรูปภาพ: ถอดเนื้อหาของแต่ละรูปเป็นข้อความ ระบุชื่อไฟล์รูป ส่วนที่อ่านไม่ชัดให้เขียนว่า "(อ่านไม่ชัด)">
<กรณีสัมภาษณ์เก็บความต้องการ: บันทึกคำถามและคำตอบของผู้ใช้ตามถ้อยคำเดิมแยกตามหมวดหมู่ หากยังสัมภาษณ์ไม่จบให้ระบุบรรทัดสุดท้ายว่า "หัวข้อถัดไป: ...">

## 2. ข้อแก้ไขและคำตอบที่ผู้ใช้ยืนยันเพิ่มเติม

| วันที่ | เรื่อง | คำตอบตามถ้อยคำจริง | ผู้ตอบและอำนาจยืนยัน | หลักฐานอ้างอิง |
|---|---|---|---|---|
| <วันที่> | <เรื่อง> | <คำตอบ> | <เจ้าของระบบ/ผู้รับจ้าง/ยังไม่ทราบ> | <ข้อความหรือเอกสารที่เกี่ยวข้อง> |

## 3. สิ่งที่ข้อกำหนดต้นทางไม่ได้ระบุไว้

<รายการสั้นๆ ของเรื่องที่ทีมวิเคราะห์และเสนอเพิ่ม รายละเอียดของแต่ละเรื่องอยู่ในไฟล์ประเด็นตัดสินใจ>

## 4. สถานะงานและจุดที่จะทำต่อ
**ช่วงงาน:** <สัมภาษณ์ / เขียนความต้องการ / ออกแบบ / รีวิว / ส่งมอบ>
**หัวข้อถัดไป:** <หมวดหรือขั้นที่ AI จะทำต่อ หรือ "ไม่มี" เมื่อเขียนครบและส่งมอบแล้ว (ขั้นที่ 0 ใช้บรรทัดนี้ตัดสินว่างานค้างหรือไม่)>
**เรื่องที่ยังขวางงาน:** <ประเด็นที่รอคนอื่นตอบ และส่วนงานที่กระทบ หรือไม่มี>
````

## 3. `{{features}}` รายการฟีเจอร์

เขียนเป็นรายการเลขลำดับชั้น (`1.1.1`, `1.1.2`) ไม่ใช้ตารางหลายคอลัมน์สำหรับตัวรายการฟีเจอร์ เพื่อให้ผู้อ่านไล่อ่านจากบนลงล่างและนำไปคุยตกลงกับลูกค้าหรือกรรมการตรวจรับได้ทีละข้อ

````markdown

ไฟล์นี้เป็นเอกสารต้นทางของรายการฟีเจอร์ เมื่อแก้ไขแล้วให้ไล่ผลกระทบไปยังเอกสารอื่นตามตารางใน {{overview}}

- ข้อที่มีคำว่า **(เฟสหลัง)** ยังไม่ทำในรอบแรก
- ข้อที่มีคำว่า **(รอยืนยัน)** คือสิ่งที่ทีมเสนอไว้ก่อน รายละเอียดอยู่ใน {{decisions}}

### 1.1 <หมวดงาน>
````

````markdown
# รายการ API และงานตั้งเวลา (API Specification & Scheduler)

<ระบุรูปแบบสัญญาและการยืนยันตัวตนที่เลือกตามจริง ไม่บังคับ REST/JSON จากตัวอย่างนี้ ถ้าใช้ RPC, GraphQL, event หรือวิธีอื่นให้ปรับแม่แบบ>

รหัสสถานะมาตรฐาน: `200 OK`, `201 Created`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `500 Internal Server Error`

รูปแบบการตอบกลับเมื่อเกิดข้อผิดพลาด (Error Response):
```json
{
  "error_code": "INVALID_STATUS_TRANSITION",

การยืนยันตัวตน: <เช่น Bearer Token / Session Cookie>

### 1.1 <หมวดย่อย>
| Method | Path | ใครเรียกได้ | คำอธิบาย (ข้อมูลเข้า / ข้อมูลออก / เงื่อนไขปฏิเสธ) |
|---|---|---|---|
| POST | `/<path>` | <บทบาท> | <รับอะไร ทำอะไร ตอบอะไร และปฏิเสธเมื่อใด> |

### 1.2 สัญญาของ <ชื่อการกระทำ>
อ้างอิงรายการในตารางด้านบนและฟีเจอร์ <ไฟล์จริงและเลขข้อ>

**ผู้เรียกและสิทธิ์:** <วิธียืนยันตัวตน บทบาท และขอบเขตข้อมูล เช่น ของตนเอง/ของหน่วยงาน/ทั้งหมด การมีบทบาทอย่างเดียวไม่ใช่สิทธิ์เข้าถึงทุกรายการ>
**เงื่อนไขก่อนทำ:** <สถานะ/เงื่อนไขที่ต้องผ่าน และผลเมื่อไม่ผ่าน>

**ข้อมูลเข้า**
| รายการและตำแหน่ง | ชนิด/รูปแบบ | ต้องส่งหรือไม่/ค่าเริ่มต้น | เงื่อนไขตรวจสอบ |
|---|---|---|---|
| <path/query/body/header หรือรูปแบบที่เลือกจริง> | <type และหน่วย> | <บังคับ/ไม่บังคับ/ค่าเริ่มต้น> | <ช่วงค่า ความยาว ความสัมพันธ์ หรืออ้างกฎ> |

**ผลผิดพลาด:** <เงื่อนไข รหัสข้อผิดพลาด ข้อมูลตอบกลับ และสิ่งที่ผู้เรียกควรทำ รวมการไม่มีสิทธิ์/ไม่พบ/สถานะเปลี่ยนไปแล้วตามที่เกี่ยวข้อง>
````
