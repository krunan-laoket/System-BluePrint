# โครงสร้างมาตรฐานของเอกสารแต่ละไฟล์

โครงเหล่านี้คือรูปแบบมาตรฐานที่อ่านเข้าใจง่ายทั้งสำหรับฝ่ายธุรกิจและทีมพัฒนา ปรับหัวข้อย่อยได้ตามลักษณะจริงของระบบ **ถ้าหัวข้อใดไม่มีเนื้อหาสำหรับระบบนี้ให้ตัดออก ห้ามเว้นหัวข้อว่างไว้**
ข้อความใน `<...>` คือส่วนที่ต้องแทนที่ด้วยเนื้อหาจริงของระบบ (ห้ามปล่อย `<...>` ค้างไว้ในเอกสารจริง)

## สารบัญโครงสร้างไฟล์

1. `00-source.md` — ข้อมูลต้นทางและบันทึกการสัมภาษณ์
2. `01-overview.md` — ภาพรวมโครงการ เป้าหมาย ขอบเขต และการส่งมอบ
3. `02-features.md` — รายการฟีเจอร์และตารางสิทธิ์
4. `03-flows.md` — ลำดับการทำงาน สถานะ และค่าที่ตั้งได้ในระบบ
5. `04-architecture.md` — สถาปัตยกรรมระบบและเป้าหมายด้านคุณภาพ
6. `05-data-model.md` — โครงสร้างข้อมูลและข้อมูลตั้งต้น
7. `06-api-spec.md` — รายการ API และงานตั้งเวลา
8. ไฟล์การเชื่อมต่อภายนอก ฮาร์ดแวร์ ข้อความแจ้งเตือน และกติกาการคำนวณ
9. `screens.md` — รายการหน้าจอ
10. `decisions.md` — ประเด็นที่ต้องตัดสินใจและบันทึกการตัดสินใจ
11. `development-plan.md` — แผนพัฒนาระบบและบริหารความเสี่ยง
12. `reports.md` — รายงาน
13. `security-pdpa.md`, `migration.md`, และ `acceptance.md` (พร้อมเมทริกซ์สอบกลับ)
14. `plans/mockup-plan.md` — แผนจัดทำ Mockup หน้าจอ
15. `README.md` — ทางเข้าหลัก สถานะเอกสาร และหน้ารับรองฉบับ

## 1. `00-source.md` ข้อมูลต้นทางและบันทึกการสัมภาษณ์

ไฟล์นี้ทำให้ตรวจสอบย้อนกลับได้ว่าเอกสารทั้งชุดมีที่มาอย่างไร ใช้เป็นฐานของการรีวิวในขั้นที่ 5 และใช้เก็บประวัติการสัมภาษณ์กรณีคุยหลายรอบ

```markdown
# ข้อมูลต้นทาง (Source Requirements)

บันทึกสิ่งที่ได้รับเป็นข้อกำหนดตั้งต้นของระบบนี้ เอกสารอื่นในชุดนี้ตีความและขยายผลจากไฟล์นี้

| รายการ | ค่า |
|---|---|
| ได้รับเมื่อ | <วันที่> |
| ได้รับจาก | <ผู้ใช้ / ลูกค้า / หน่วยงาน ตามที่ผู้ใช้แจ้ง> |
| บริบทองค์กร | <สถานศึกษา / บริษัทเอกชน / หน่วยงานราชการหรือรัฐวิสาหกิจ / อื่นๆ> |
| รูปแบบต้นทาง | <พิมพ์ในแชต / สัมภาษณ์เก็บความต้องการ / ไฟล์ในโฟลเดอร์ ... / รูปภาพ N รูป> |

## 1. สิ่งที่ได้รับจากต้นทาง

<กรณีพิมพ์ในแชต: คัดข้อความของผู้ใช้มาตามเดิม ไม่เรียบเรียงใหม่>
<กรณีโฟลเดอร์ที่อยู่ในโครงการ: ตารางชื่อไฟล์ และสรุปเนื้อหาไฟล์ละ 1–2 บรรทัด ไม่ต้องคัดลอกทั้งไฟล์เพราะต้นฉบับอยู่ในโครงการ>
<กรณีโฟลเดอร์ที่อยู่นอกโครงการ: ตารางชื่อไฟล์ แล้วคัดข้อกำหนดทุกข้อลงมาตามเดิม เพราะต้นฉบับจะไม่ติดไปกับชุดเอกสาร>
<กรณีรูปภาพ: ถอดเนื้อหาของแต่ละรูปเป็นข้อความ ระบุชื่อไฟล์รูป ส่วนที่อ่านไม่ชัดให้เขียนว่า "(อ่านไม่ชัด)">
<กรณีสัมภาษณ์เก็บความต้องการ: บันทึกคำถามและคำตอบของผู้ใช้ตามถ้อยคำเดิมแยกตามหมวดหมู่ หากยังสัมภาษณ์ไม่จบให้ระบุบรรทัดสุดท้ายว่า "หัวข้อถัดไป: ...">

## 2. ข้อแก้ไขและคำตอบที่ผู้ใช้ยืนยันเพิ่มเติม

| วันที่ | เรื่อง | คำตอบของผู้ใช้ |
|---|---|---|
| <วันที่> | <เช่น ขอบเขตการชำระเงิน หรือคำว่า X ในข้อกำหนดหมายถึงอะไร> | <คำตอบของผู้ใช้> |

## 3. สิ่งที่ข้อกำหนดต้นทางไม่ได้ระบุไว้

<รายการสั้นๆ ของเรื่องที่ทีมวิเคราะห์และเสนอเพิ่ม รายละเอียดของแต่ละเรื่องอยู่ในไฟล์ประเด็นตัดสินใจ>
```

## 3. `02-features.md` รายการฟีเจอร์

เขียนเป็นรายการเลขลำดับชั้น (`1.1.1`, `1.1.2`) ไม่ใช้ตารางหลายคอลัมน์สำหรับตัวรายการฟีเจอร์ เพื่อให้ผู้อ่านไล่อ่านจากบนลงล่างและนำไปคุยตกลงกับลูกค้าหรือกรรมการตรวจรับได้ทีละข้อ

```markdown
# รายการฟีเจอร์<ชื่อระบบ>

ไฟล์นี้เป็นเอกสารต้นทางของรายการฟีเจอร์ เมื่อแก้ไขแล้วให้ไล่ผลกระทบไปยังเอกสารอื่นตามตารางใน 01-overview.md

- ข้อที่มีคำว่า **(เฟสหลัง)** ยังไม่ทำในรอบแรก
- ข้อที่มีคำว่า **(รอยืนยัน)** คือสิ่งที่ทีมเสนอไว้ก่อน รายละเอียดอยู่ใน<ชื่อไฟล์ประเด็นตัดสินใจ>
<ถ้าข้อเสนอของทีมมีมากกว่าครึ่งหนึ่งของไฟล์ ให้สลับเป็นทำเครื่องหมาย (ลูกค้ากำหนด) เฉพาะข้อที่มาจากต้นทาง และประกาศไว้ตรงนี้ว่าข้อที่ไม่มีเครื่องหมายคือข้อเสนอของทีม>

## 1. <กลุ่มผู้ใช้ที่ 1> (ผ่าน<ช่องทาง>)

### 1.1 <หมวดงาน>
- 1.1.1 <ผู้ใช้ทำอะไรได้ 1 ประโยค ขึ้นต้นด้วยคำกริยา วัดผลได้>
- 1.1.2 <...>

## 2. <กลุ่มผู้ใช้ที่ 2> (ผ่าน<ช่องทาง>)

### 2.1 <หมวดงาน>
- 2.1.1 <...>

## <N>. สิ่งที่ระบบทำเองอัตโนมัติ
- <N>.1 <งานที่ระบบประมวลผลหรือแจ้งเตือนเองตามเงื่อนไขเวลาหรือเหตุการณ์>

## <N+1>. สรุปสิทธิ์ของแต่ละบทบาท
| หมวดงาน / ฟีเจอร์ | <บทบาทที่ 1> | <บทบาทที่ 2> | <บทบาทที่ 3> |
|---|---|---|---|
| <ชื่อหมวดหรือฟีเจอร์> | ทำได้ / ดูได้ / ไม่ได้ | ... | ... |

## หมายเหตุ
- **ที่มาของฟีเจอร์:** <สรุปว่าส่วนใดมาจากข้อกำหนดของลูกค้า ส่วนใดทีมเสนอเพิ่มเพื่อให้ระบบทำงานครบวงจร>
- **ฟีเจอร์ที่พิจารณาแล้วยังไม่รวมในระบบนี้ (ถ้ามี):** <ระบุพร้อมเหตุผล เพื่อป้องกันการเข้าใจผิดซ้ำ>
```

*หลักการเขียนฟีเจอร์:*
- ไฟล์อื่นอ้างถึงฟีเจอร์ได้ทั้งระดับหมวด (`02-features.md ข้อ 1.1`) และระดับข้อย่อย (`02-features.md ข้อ 1.1.2`) สคริปต์ตรวจรองรับทั้งสองแบบ
- เขียนในมุมสิ่งที่ผู้ใช้ทำได้หรือได้รับทางธุรกิจ เช่น `"ยกเลิกการจองด้วยตนเองภายในเวลาที่กำหนด"` ไม่เขียนเป็นศัพท์เทคนิคเช่น `"มี Endpoint สำหรับยกเลิก"`
