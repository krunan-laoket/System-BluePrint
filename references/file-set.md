# การเลือกรายการไฟล์และโหมดความลึกของเอกสาร

รายการไฟล์ไม่ตายตัว เลือกตามลักษณะจริงของระบบและเป้าหมายของผู้ใช้ หลักการคือ **ทุกเรื่องที่ทีมและผู้เกี่ยวข้องต้องรู้เพื่อตัดสินใจหรือเริ่มงานต้องมีที่อยู่ และไม่มีไฟล์ที่ว่างเปล่าเพราะระบบไม่มีเรื่องนั้น**

ชื่อและเลขในตารางเป็นตัวอย่างของโครงการใหม่ **บทบาทใน `blueprint.json` เป็นตัวบอกความหมาย ไม่ใช่เลขนำหน้า** เมื่ออัปเกรดหรือต่องานให้ใช้ path จริงจากทะเบียนแทนชื่อในตัวอย่างทุกแห่ง

## 1. ไฟล์แกน (มีในทุกโครงการ)

| ไฟล์ | เนื้อหาหลัก | ผู้อ่านหลัก | โหมดที่ใช้ |
|---|---|---|---|
| `docs/00-source.md` | บันทึกข้อมูลต้นทางที่ได้รับ คำตอบจากการสัมภาษณ์ และข้อแก้ไขที่ผู้ใช้ยืนยัน | ผู้รีวิว ทีมวิเคราะห์ | ทุกโหมด |
| `docs/01-overview.md` | ภาพรวม ที่มา เป้าหมายที่วัดได้ ขอบเขต ผู้ใช้และผู้มีส่วนได้ส่วนเสีย ข้อจำกัด การส่งมอบ/SLA และคำศัพท์กลาง | ทุกคน ผู้บริหาร | ทุกโหมด |

| `docs/03-flows.md` | ลำดับการทำงานแต่ละเรื่อง กรณีผิดปกติ ตารางสถานะ ผังสถานะ และตารางค่าที่ตั้งได้ในระบบ | ทุกคน | ทุกโหมด |
| ไฟล์บทบาท `architecture` เช่น `docs/04-architecture.md` | ส่วนประกอบ การสื่อสาร เทคโนโลยี สภาพแวดล้อม และวิธีรองรับคุณภาพที่กำหนดในภาพรวม | นักพัฒนา สถาปนิก | โหมดครบวงจร |
| `docs/05-data-model.md` | แผนภาพความสัมพันธ์ (ER Diagram) รายละเอียด Entity/ฟิลด์/Enum และข้อมูลตั้งต้นก่อนเปิดใช้ | นักพัฒนา | โหมดครบวงจร |
| `docs/06-api-spec.md` | รายการ API แยกตามฝั่งผู้ใช้ งานตั้งเวลา (Scheduler) และรหัส Error | นักพัฒนา | โหมดครบวงจร |
| ไฟล์ประเด็นตัดสินใจ (`XX-decisions.md`) | ทุกเรื่องที่ต้องยืนยันกับลูกค้า/ผู้มีอำนาจ ทางเลือก คำแนะนำ และไฟล์ที่ได้รับผลกระทบ | หัวหน้าโครงการ ลูกค้า ผู้บริหาร | ทุกโหมด |
| ไฟล์แผนพัฒนา (`XX-development-plan.md`) | การแบ่งเฟส งานส่งมอบ เกณฑ์ผ่าน ความเสี่ยง และสิ่งที่ต้องได้รับจากลูกค้า | หัวหน้าโครงการ ทีมพัฒนา | ทุกโหมด |
| ไฟล์บทบาท `acceptance` (`XX-acceptance.md`) | เกณฑ์ตรวจรับฟีเจอร์ คุณภาพ สิ่งส่งมอบ และเมทริกซ์สอบกลับ | เจ้าของระบบ ผู้ตรวจรับ ทีมพัฒนา | ทุกโหมด |
| `README.md` | ทางเข้าหลักของทั้งชุด โครงสร้างไฟล์ เริ่มอ่านที่ไหน ข้อควรรู้ และหน้ารับรองฉบับ | ทุกคน | ทุกโหมด |
| `blueprint.json` | โหมดและทะเบียนบทบาท/ชื่อไฟล์จริงตามรูปแบบด้านล่าง | ตัวตรวจและผู้จัดทำเอกสาร | ทุกโหมด |
| `plans/` (อย่างน้อย 1 ไฟล์) | แผนปฏิบัติการขั้นถัดไป เช่น `plans/mockup-plan.md` หรือแผนเตรียมการทดสอบ/ขออนุมัติ | ผู้ที่จะทำงานขั้นถัดไป | ทุกโหมด |

### ข้อยกเว้นการตัดหรือปรับไฟล์แกน
- **full ไม่มี API:** ไม่สร้างบทบาท api ระบุเหตุผลใน `omissions.api` และ README งานตั้งเวลาอยู่ที่ architecture ไม่ต้องเพิ่ม API เพื่อให้ครบไฟล์
- **business:** ไม่สร้าง architecture/data_model/api คุณภาพที่วัดได้และกลุ่มข้อมูลหลักระดับธุรกิจอยู่ที่ overview ส่วน full ก็เก็บข้อกำหนดนี้ที่เดิม ให้ architecture อ้างวิธีรองรับ จึงไม่ต้องย้ายหรือคัดลอกเมื่ออัปเกรด
- full ที่ไม่เก็บข้อมูลถาวร ให้ data_model อธิบายสัญญาข้อมูลเข้าออก/ไฟล์/สถานะในหน่วยความจำตามจริง ไม่บังคับฐานข้อมูลหรือ ER diagram

## 2. ไฟล์เสริม (เลือกเฉพาะเมื่อระบบมีเรื่องนั้นจริง)

ถามตัวเองทีละข้อตามตารางนี้ ถ้าคำตอบคือ **ใช่** ให้เพิ่มไฟล์นั้นเข้าไปใน `docs/` ไม่มีเพดานจำนวนไฟล์:

| ระบบมีสิ่งนี้หรือไม่ | ชื่อไฟล์ที่เพิ่ม (หลังเลขนำหน้า) | เนื้อหาหลัก |
|---|---|---|
| มีหน้าจอให้คนใช้งาน | `screens.md` | business ระบุข้อมูลและการกระทำระดับธุรกิจ; full เพิ่ม API ที่เชื่อมเมื่อมี |
| มีกติกาการคำนวณหรือกฎธุรกิจที่ซับซ้อน (เช่น ราคา ส่วนลด ค่าปรับ คะแนน โควตา สิทธิ์) | `business-rules.md` | กติกาแต่ละข้อ สูตรคำนวณ ตารางตัวอย่างคำนวณจริง และกรณีขอบ (Edge cases) |
| เชื่อมกับแพลตฟอร์มหรือบริการภายนอกที่มีรายละเอียดมาก | 1 ไฟล์ต่อการเชื่อมต่อ ตั้งชื่อตามสิ่งที่เชื่อม เช่น `line-integration.md`, `payment.md`, `erp-integration.md`, `thaid-integration.md` | สิ่งที่ต้องเตรียม ลำดับการเรียก ข้อจำกัดของบริการ ค่าใช้จ่าย และรายการทดสอบ |
| มีฮาร์ดแวร์หรืออุปกรณ์หน้างาน (เครื่องสแกน เครื่องพิมพ์ ตู้ Kiosk IoT) | `hardware.md` | สเปกอุปกรณ์ขั้นต่ำ โปรโตคอลการเชื่อมต่อ การติดตั้ง การจัดการเมื่ออุปกรณ์ขัดข้อง และรายการทดสอบ |
| ส่งข้อความหรือแจ้งเตือนอัตโนมัติหลายรูปแบบ/หลายช่องทาง | รวมไว้ในไฟล์การเชื่อมต่อของช่องทางนั้น หรือแยกเป็น `notifications.md` | ช่องทางที่ใช้ ตารางข้อความทั้งหมด (ส่งเมื่อใด ส่งถึงใคร ถ้อยคำตั้งต้น ปุ่ม/ลิงก์) กติกาการส่งซ้ำ และค่าใช้จ่าย |
| ลูกค้ากำหนดรูปแบบรายงานเฉพาะเจาะจง หรือรายงานเป็นงานส่งมอบสำคัญ | `reports.md` | รายงานแต่ละฉบับ ผู้มีสิทธิ์ดู รูปแบบตารางพร้อมแถวตัวอย่าง วิธีนับแต่ละช่อง และกรณีขอบ |
| เก็บข้อมูลส่วนบุคคล หรือมีข้อกำหนดด้านกฎหมาย/PDPA/ความปลอดภัยเข้มงวด | `security-pdpa.md` หรือ `security.md` | ข้อมูลส่วนบุคคลที่เก็บและฐานกฎหมาย การขอความยินยอม สิทธิ์การเข้าถึงและการปกปิดข้อมูล อายุการเก็บ ประวัติการใช้งาน (Log) และแนวทางรับมือเมื่อข้อมูลรั่วไหล |
| มาแทนระบบเดิม หรือต้องนำเข้าข้อมูลเก่าจำนวนมาก | `migration.md` | ข้อมูลที่ย้ายและไม่ย้าย ตารางจับคู่ฟิลด์เดิมกับฟิลด์ใหม่ การทำความสะอาดข้อมูล ลำดับการย้าย การตรวจหลังย้าย และแผนถอยกลับ |

*หมายเหตุ:* เรื่องเล็กที่มีรายละเอียดเพียงไม่กี่บรรทัด (เช่น ระบบส่งอีเมลแจ้งเตือนแค่ 1–2 แบบ หรือมีกฎคำนวณง่ายๆ ข้อเดียว) ไม่ต้องแยกเป็นไฟล์ใหม่ ให้ใส่เป็นหัวข้อในไฟล์แกนที่ใกล้เคียงที่สุด

ทุกไฟล์เสริมต้องปรับระดับรายละเอียดตามโหมด: business ใช้กลุ่มข้อมูล/การกระทำ/เงื่อนไข; full เพิ่มฟิลด์ schema protocol หรือ API ตามที่ออกแบบจริง ไม่คัดรายละเอียดเทคนิคจากแม่แบบลง business

## 3. กฎการเรียงเลขนำหน้าไฟล์ใน `docs/`

สคริปต์ตรวจ (`scripts/check_docs.py`) จะตรวจสอบการเรียงเลขไฟล์อย่างเข้มงวด ให้ใช้กฎนี้เสมอ:
1. ใช้ **เลข 2 หลัก เรียงต่อเนื่องกันโดยไม่ข้ามเลข** (เริ่มที่ `00` ไปจนถึงไฟล์สุดท้าย เช่น `00`, `01`, `02`, `03`, ..., `11`)
2. ชื่อไฟล์ใช้ภาษาอังกฤษตัวพิมพ์เล็ก คั่นคำด้วยขีดกลาง (`-`) เช่น `07-business-rules.md`
3. **ลำดับการวางเลขไฟล์:**
   - โครงการใหม่เริ่ม source, overview, features, flows แล้วเพิ่มเทคนิคเฉพาะ full ตามลำดับในตาราง เลข 04/05/06 ไม่เป็นข้อบังคับของงานเก่าหรืองานอัปเกรด
   - ถัดมาคือไฟล์เสริมที่ลำดับการทำงานและหน้าจอต้องอ้างอิง ได้แก่ ไฟล์การเชื่อมต่อภายนอก ฮาร์ดแวร์ ข้อความแจ้งเตือน และกติกาการคำนวณ (ถ้ามี)
   - ตามด้วย `screens.md` (รายการหน้าจอ)
   - ตามด้วย `decisions.md` (ประเด็นตัดสินใจ) และ `development-plan.md` (แผนพัฒนา)
   - ปิดท้ายด้วยไฟล์ส่งมอบ/กำกับดูแลตามที่มี และ acceptance ที่มีทุกโครงการ
4. หากต้องเพิ่มไฟล์ใหม่หลังจากที่ไฟล์อื่นเขียนและอ้างอิงเลขไฟล์ไปแล้ว **ให้เพิ่มต่อท้ายเป็นเลขถัดไปเสมอ ห้ามแทรกกลาง** เพื่อไม่ให้เลขไฟล์เดิมเคลื่อน

## 4. ทะเบียน `blueprint.json`

เป็น JSON UTF-8 ที่รากโครงการ ไม่เก็บข้อกำหนดซ้ำ เขียน README ให้คนอ่านรู้โหมดและรายการไฟล์ได้โดยไม่ต้องอ่าน JSON

```json
{
  "schema_version": 1,
  "mode": "business",
  "documents": {
    "source": "docs/00-source.md",
    "overview": "docs/01-overview.md",
    "features": "docs/02-features.md",
    "flows": "docs/03-flows.md",
    "screens": "docs/04-screens.md",
    "decisions": "docs/05-decisions.md",
    "development_plan": "docs/06-development-plan.md",
    "acceptance": "docs/07-acceptance.md"
  },
  "plans": ["plans/next-step.md"],
  "omissions": {}
}
```

- `schema_version` เป็นจำนวนเต็ม 1, `mode` เป็น `business` หรือ `full`
- ทุกโหมดมีบทบาท source, overview, features, flows, decisions, development_plan และ acceptance; full เพิ่ม architecture, data_model และ api (เว้นได้เฉพาะ api พร้อมเหตุผล)
- documents จับคู่บทบาทกับ path จริง หนึ่งบทบาทต่อหนึ่งไฟล์ ห้าม path ซ้ำ บทบาทเสริมตั้งชื่อสื่อความหมาย เช่น screens, security, migration, integration_line
- plans เป็นรายการแผน Markdown จริงอย่างน้อยหนึ่งไฟล์ ทุกไฟล์ Markdown ใน docs/plans ต้องอยู่ในทะเบียน
- omissions รับเฉพาะ api พร้อมเหตุผลใน full ที่ไม่มี API ห้ามระบุเว้น api พร้อมกับสร้างบทบาท api
- path เป็น relative ใช้ `/` อยู่ภายในโครงการ ชี้ไฟล์ `.md` ที่มีเนื้อหาใน docs/ หรือ plans/ ตามประเภท ห้ามใช้ symlink ออกนอกโครงการ
- ชื่อ docs เริ่มเลข 00 ต่อเนื่องตามกฎข้างบน เลขไม่ผูกกับบทบาท; source อาจมีเลขเดิมที่ต่างจากตัวอย่างได้เมื่อรับงานเก่า

**ตัวอย่างอัปเกรด:** คงไฟล์ 00–07 ในตัวอย่าง เพิ่ม `08-architecture.md`, `09-data-model.md`, `10-api-spec.md` ใน docs แล้วเปลี่ยน mode เป็น full และเพิ่มบทบาททั้งสาม ห้ามย้าย screens/decisions เดิมกลับไปเลขอื่น ทุกแม่แบบและการอ้างต้องใช้ชื่อใหม่ในทะเบียน

**ชุดเดิมไม่มีทะเบียน:** จับคู่กับไฟล์จริงและรักษาประวัติ ถ้าต้องเปลี่ยนชื่อเพื่อให้เข้ารูปแบบ ให้เสนอแผนและผลกระทบก่อน ตัวตรวจไม่แก้หรือย้ายไฟล์เอง ชุดที่ไม่มีทะเบียนหรือยังเขียนไม่ครบยังไม่ผ่านการตรวจส่งมอบ แต่บันทึกงานระหว่างทางได้

แผนใน plans เลือกตามขั้นถัดไป: Mockup เมื่อมีหน้าจอ แผนทดลองเมื่อมีความเสี่ยงเทคนิค หรือแผนยืนยันขอบเขต/ขออนุมัติใน business ไม่บังคับ Mockup กับระบบที่ไม่มีหน้าจอ
