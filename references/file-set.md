# การเลือกรายการไฟล์ ชื่อบทบาท และทะเบียน `blueprint.json`

รายการไฟล์ไม่ตายตัว เลือกตามลักษณะจริงของระบบ หลักการคือ **ทุกเรื่องที่ผู้เกี่ยวข้องต้องรู้เพื่อตัดสินใจหรือเริ่มงานต้องมีที่อยู่ และไม่มีไฟล์ที่ว่างเพราะระบบไม่มีเรื่องนั้น**

แต่ละไฟล์มี **บทบาท (role)** ในทะเบียน เช่น `features` บทบาทเป็นตัวบอกความหมาย ไม่ใช่เลขนำหน้า ในไฟล์อ้างอิงของสกิลนี้ `{{features}}` หมายถึง path จริงของบทบาทนั้น เช่น `docs/02-features.md` ชื่อและเลขในตารางด้านล่างเป็นตัวอย่างของโครงการใหม่ งานต่อหรืองานอัปเกรดให้ใช้ path จริงจากทะเบียนเสมอ

---

## 1. ไฟล์แกน

| บทบาท | ชื่อไฟล์ตัวอย่าง | เนื้อหาหลัก | โหมด |
|---|---|---|---|
| `source` | `docs/00-source.md` | ข้อมูลต้นทาง ทะเบียนแหล่งข้อมูล คำตอบสัมภาษณ์ตามถ้อยคำจริง และสถานะงาน | ทุกโหมด |
| `overview` | `docs/01-overview.md` | ที่มา เป้าหมายที่วัดได้ ขอบเขต ผู้ใช้ ข้อจำกัด การส่งมอบ คำศัพท์กลาง คุณภาพที่วัดได้ และกลุ่มข้อมูลระดับธุรกิจ | ทุกโหมด |
| `features` | `docs/02-features.md` | ฟีเจอร์แยกตามกลุ่มผู้ใช้ งานอัตโนมัติ และตารางสิทธิ์ | ทุกโหมด |
| `flows` | `docs/03-flows.md` | ลำดับงาน กรณีผิดปกติ ตารางสถานะ และตารางค่าที่ตั้งได้ในระบบ | ทุกโหมด |
| `architecture` | `docs/04-architecture.md` | ส่วนประกอบ การสื่อสาร ข้อเสนอเทคโนโลยี สภาพแวดล้อม และวิธีรองรับคุณภาพใน overview | full |
| `data_model` | `docs/05-data-model.md` | Entity ฟิลด์ ค่าสถานะ และข้อมูลตั้งต้น | full |
| `api` | `docs/06-api-spec.md` | รายการ API งานตั้งเวลา และรหัส Error | full (เว้นได้ถ้าไม่มี API) |
| `decisions` | `docs/NN-decisions.md` | ประเด็นที่ต้องตัดสินใจ ทางเลือก คำแนะนำ ผู้ยืนยัน และไฟล์ที่ได้รับผลกระทบ | ทุกโหมด |
| `development_plan` | `docs/NN-development-plan.md` | เฟส งานส่งมอบ เกณฑ์ผ่าน ความเสี่ยง และสิ่งที่ต้องได้รับจากลูกค้า | ทุกโหมด |
| `acceptance` | `docs/NN-acceptance.md` | สถานการณ์ตรวจรับ เมทริกซ์สอบกลับ และการตรวจรับคุณภาพ/สิ่งส่งมอบ | ทุกโหมด |
| (ไม่มีบทบาท) | `README.md` | ทางเข้าหลัก รายการไฟล์ ลำดับการอ่าน ผลตรวจ และหน้ารับรองฉบับ | ทุกโหมด |
| (ไม่มีบทบาท) | `blueprint.json` | ทะเบียนตามหัวข้อ 4 | ทุกโหมด |
| (ใน `plans`) | `plans/<ชื่อแผน>.md` อย่างน้อย 1 ไฟล์ | แผนขั้นถัดไป: แผนยืนยันขอบเขต/ขออนุมัติ (business) แผนทำ Mockup (เมื่อมีหน้าจอ) หรือแผนทดลองเทคนิค (เมื่อมีความเสี่ยงเทคนิค) | ทุกโหมด |

`NN` คือเลขถัดไปตามกฎหัวข้อ 3

**ข้อยกเว้น**
- **full ที่ไม่มี API:** ไม่สร้างบทบาท `api` ระบุเหตุผลใน `omissions.api` และใน README งานตั้งเวลาย้ายไปอธิบายใน architecture
- **business:** ไม่สร้าง architecture, data_model, api คุณภาพที่วัดได้และกลุ่มข้อมูลอยู่ใน overview ซึ่งเป็นเจ้าของข้อกำหนดนี้ทั้งสองโหมด เมื่ออัปเกรดเป็น full จึงไม่ต้องย้าย ให้ architecture และ data_model อ้างกลับมาที่ overview
- **full ที่ไม่เก็บข้อมูลถาวร:** data_model อธิบายข้อมูลเข้าออก ไฟล์ หรือสถานะในหน่วยความจำตามจริง ไม่บังคับฐานข้อมูลหรือ ER diagram

## 2. ไฟล์เสริม (เพิ่มเฉพาะเมื่อระบบมีเรื่องนั้นจริง)

ถามตัวเองทีละข้อ ถ้าใช่ ให้เพิ่มไฟล์ใน `docs/` และลงทะเบียนด้วย **ชื่อบทบาทตามตารางนี้** (ตัวตรวจนับจำนวนหน้าจอจากบทบาท `screens`) แยกเท่าที่จำเป็น รูปแบบเลข 00–99 รองรับได้ 100 ไฟล์ใน docs/ ถ้าใกล้เต็มให้ทบทวนการแบ่งชุดเอกสารก่อนเพิ่ม ห้ามเลื่อนเลขเดิมเอง

| ระบบมีสิ่งนี้หรือไม่ | บทบาท | ชื่อไฟล์ (หลังเลขนำหน้า) | เนื้อหาหลัก |
|---|---|---|---|
| มีหน้าจอให้คนใช้งาน | `screens` | `screens.md` | หน้าจอ ข้อมูลและการกระทำหลัก สิทธิ์ ความสำคัญ (full ที่มี API เพิ่มคอลัมน์ API) |
| กติกาการคำนวณหรือกฎธุรกิจซับซ้อน (ราคา ส่วนลด ค่าปรับ คะแนน โควตา) | `business_rules` | `business-rules.md` | กติกา สูตร ตัวอย่างคำนวณจริง และกรณีขอบ |
| เชื่อมบริการภายนอกที่มีรายละเอียดมาก | `integration_<ชื่อ>` เช่น `integration_line` | `<ชื่อ>-integration.md` เช่น `line-integration.md` | สิ่งที่ต้องเตรียม ลำดับการทำงาน ข้อจำกัด ค่าใช้จ่าย รายการทดสอบ (1 ไฟล์ต่อการเชื่อมต่อ) |
| ฮาร์ดแวร์หน้างาน (เครื่องสแกน เครื่องพิมพ์ Kiosk IoT) | `hardware` | `hardware.md` | สเปกขั้นต่ำ การเชื่อมต่อ การติดตั้ง เมื่ออุปกรณ์ขัดข้อง รายการทดสอบ |
| แจ้งเตือนหลายแบบหลายช่องทาง | `notifications` | `notifications.md` | ตารางข้อความทั้งหมด ส่งเมื่อใด ถึงใคร ถ้อยคำ การส่งซ้ำ ค่าใช้จ่าย |
| รายงานเป็นงานส่งมอบสำคัญหรือลูกค้ากำหนดรูปแบบ | `reports` | `reports.md` | รายงานแต่ละฉบับ ผู้มีสิทธิ์ดู ตารางพร้อมแถวตัวอย่าง วิธีนับแต่ละช่อง |
| เก็บข้อมูลส่วนบุคคลจำนวนมากหรือข้อมูลอ่อนไหว มีการขอความยินยอม หรือข้อกำหนดความปลอดภัยเข้มงวด (ข้อมูลส่วนบุคคลไม่กี่ช่องและไม่อ่อนไหว ให้เป็นหัวข้อในภาพรวมแทน ดูตัวอย่าง) | `security` | `security-pdpa.md` | ข้อมูลส่วนบุคคลและฐานกฎหมาย ความยินยอม สิทธิ์การเข้าถึง อายุการเก็บ Log และการรับมือข้อมูลรั่วไหล |
| แทนระบบเดิม หรือนำเข้าข้อมูลเก่าจำนวนมาก | `migration` | `migration.md` | ข้อมูลที่ย้ายและไม่ย้าย การจับคู่ การทำความสะอาด ลำดับการย้าย การตรวจหลังย้าย แผนถอยกลับ |

- เรื่องเล็กที่มีไม่กี่บรรทัด (เช่น อีเมลแจ้งเตือน 1–2 แบบ หรือกฎคำนวณข้อเดียว) ไม่ต้องแยกไฟล์ ให้เป็นหัวข้อในไฟล์แกนที่ใกล้ที่สุด
- ระดับรายละเอียดตามโหมด: business ใช้กลุ่มข้อมูล การกระทำ และเงื่อนไขทางธุรกิจ full จึงเพิ่มฟิลด์ protocol หรือ API ตามที่ออกแบบจริง

## 3. กฎการตั้งชื่อและเรียงเลขไฟล์ใน `docs/`

ตัวตรวจ (`scripts/check_docs.py`) บังคับกฎนี้:
1. ชื่อไฟล์เป็น `เลข 2 หลัก-ชื่อภาษาอังกฤษตัวพิมพ์เล็กคั่นด้วยขีดกลาง.md` เช่น `07-business-rules.md` ไม่มีโฟลเดอร์ย่อยใน `docs/`
2. เลขเริ่มที่ `00` และเรียงต่อเนื่องไม่ข้ามเลข
3. **ลำดับเลขของโครงการใหม่:** source → overview → features → flows → (full: architecture → data_model → api) → ไฟล์เสริมด้านกฎและการเชื่อมต่อ (business_rules, integration, hardware, notifications, security, migration, reports) → screens → decisions → development_plan → acceptance
4. **ไฟล์ที่เพิ่มหลังจากมีการอ้างอิงแล้ว ให้ต่อท้ายเลขสุดท้ายเสมอ ห้ามแทรกกลาง** เพื่อไม่ให้เลขไฟล์เดิมเลื่อน (รวมถึงการอัปเกรด business เป็น full)

ตัวอย่างโครงการใหม่ business ที่มีหน้าจอและ PDPA: `00-source`, `01-overview`, `02-features`, `03-flows`, `04-security-pdpa`, `05-screens`, `06-decisions`, `07-development-plan`, `08-acceptance`

## 4. ทะเบียน `blueprint.json`

JSON แบบ UTF-8 ที่รากโครงการ ไม่เก็บข้อกำหนดซ้ำ README ต้องบอกโหมดและรายการไฟล์ให้คนอ่านรู้ได้โดยไม่ต้องเปิด JSON

```json
{
  "schema_version": 1,
  "mode": "business",
  "documents": {
    "source": "docs/00-source.md",
    "overview": "docs/01-overview.md",
    "features": "docs/02-features.md",
    "flows": "docs/03-flows.md",
    "screens": "docs/04-screens.md",
    "decisions": "docs/05-decisions.md",
    "development_plan": "docs/06-development-plan.md",
    "acceptance": "docs/07-acceptance.md"
  },
  "plans": ["plans/scope-confirmation-plan.md"],
  "omissions": {}
}
```

- `schema_version` เป็นจำนวนเต็ม `1` และ `mode` เป็น `business` หรือ `full`
- `document_style` เป็น `standard` หรือ `compact` ไม่ระบุเท่ากับ `standard` เพื่อให้ทะเบียนเดิมใช้ต่อได้ ขนาดเอกสารแยกจากโหมดความลึก
- ทุกโหมดต้องมีบทบาท source, overview, features, flows, decisions, development_plan, acceptance ส่วน full ต้องเพิ่ม architecture, data_model และ api (เว้น api ได้อย่างเดียวพร้อมเหตุผล) business ห้ามมีบทบาทเทคนิคทั้งสาม
- `documents` จับคู่บทบาทกับ path จริง แต่ละบทบาทชี้ไฟล์เดียว standard ห้าม path ซ้ำ; compact รวมได้เฉพาะคู่ overview/features และ acceptance/development_plan ตามหัวข้อ 5 ชื่อบทบาทเป็นภาษาอังกฤษตัวพิมพ์เล็กและขีดล่าง ใช้ชื่อตามตารางหัวข้อ 2
- `plans` เป็นรายการ path ของแผนอย่างน้อย 1 ไฟล์ **ทุกไฟล์ `.md` ใน docs/ และ plans/ ต้องอยู่ในทะเบียน**
- `omissions` รับได้เฉพาะ `{"api": "เหตุผล"}` ใน full ที่ไม่มีบทบาท api
- path เป็น relative ใช้ `/` (แม้บน Windows) อยู่ภายในโครงการ และชี้ไฟล์ `.md` ที่มีเนื้อหาใน docs/ หรือ plans/

**ตัวอย่างอัปเกรด:** จากทะเบียนข้างบน คงไฟล์ 00–07 ไว้ทั้งหมด เพิ่ม `docs/08-architecture.md`, `docs/09-data-model.md`, `docs/10-api-spec.md` เปลี่ยน `mode` เป็น `full` และเพิ่มบทบาท architecture, data_model, api ห้ามย้าย screens หรือ decisions ไปเลขอื่น แล้วตรวจทุกการอ้างอิงตามชื่อจริง (ไฟล์หน้าจอใน full ที่มี API ให้เพิ่มคอลัมน์ API)

**ชุดเดิมที่ไม่มีทะเบียน:** จับคู่บทบาทกับไฟล์จริงและรักษาประวัติ ถ้าต้องเปลี่ยนชื่อไฟล์ให้เข้ารูปแบบ ให้เสนอแผนและผลกระทบให้ผู้ใช้อนุมัติก่อน ตัวตรวจไม่แก้หรือย้ายไฟล์เอง ชุดที่ยังไม่มีทะเบียนหรือยังเขียนไม่ครบจะยังไม่ผ่านตัวตรวจ แต่บันทึกงานระหว่างทางได้

## 5. ฉบับย่อสำหรับระบบขนาดเล็ก (`document_style: compact`)

ใช้กับ business ที่มีลำดับงานหลักไม่เกิน 3 เรื่อง ไม่มีการคำนวณซับซ้อนหรือการเชื่อมต่อหลายระบบ และไม่ได้ถูกบังคับให้แยกเอกสาร ไม่ลดการสอบกลับหรือเกณฑ์ตรวจรับ ใช้เนื้อหาจากแม่แบบโดยรวมไว้ดังนี้:

| ไฟล์ | บทบาทในทะเบียน | หัวข้อที่ต้องมี |
|---|---|---|
| `docs/00-source.md` | source | ต้นทาง คำตอบ สถานะงาน และข้อมูลที่ยังไม่รู้ |
| `docs/01-scope.md` | overview, features | เป้าหมาย ขอบเขต บทบาท ฟีเจอร์/สิทธิ์ คุณภาพ กลุ่มข้อมูล ข้อจำกัดและการส่งมอบ; หน้าจอเป็นหัวข้อในไฟล์นี้เมื่อมี |
| `docs/02-flows.md` | flows | Flow ปกติ/ผิดปกติ สถานะ และค่าที่ตั้งได้ |
| `docs/03-decisions.md` | decisions | ประเด็น ทางเลือก สถานะ ผู้ยืนยัน/หลักฐาน และผลกระทบ |
| `docs/04-delivery.md` | acceptance, development_plan | สถานการณ์ตรวจรับ เมทริกซ์สอบกลับ แผนพัฒนา ความเสี่ยงและสิ่งที่รอจากผู้เกี่ยวข้อง |

ยังมี README.md, blueprint.json และแผนขั้นถัดไปใน plans/ อย่างน้อย 1 ไฟล์ แผนพัฒนาใน delivery บอกเฟสและเกณฑ์ผ่าน ส่วน plans/ บอกงานถัดไปที่ทำได้จริง ไม่คัดเนื้อหาซ้ำกัน

```json
{
  "schema_version": 1,
  "mode": "business",
  "document_style": "compact",
  "documents": {
    "source": "docs/00-source.md",
    "overview": "docs/01-scope.md",
    "features": "docs/01-scope.md",
    "flows": "docs/02-flows.md",
    "decisions": "docs/03-decisions.md",
    "acceptance": "docs/04-delivery.md",
    "development_plan": "docs/04-delivery.md"
  },
  "plans": ["plans/next-step.md"],
  "omissions": {}
}
```

- หนึ่งไฟล์ใช้เลขหัวข้อต่อเนื่องชุดเดียว ไม่เริ่มเลขใหม่ตามบทบาท อ้างชื่อไฟล์จริงและเลขหัวข้อ เช่น `01-scope.md ข้อ 4.1`
- หน้าจอที่รวมใน scope ไม่ลงทะเบียนบทบาท screens และอ้าง scope ตามเลขหัวข้อแทน `{{screens}}` ทวนจำนวนหน้าจอด้วยการอ่าน ตารางนับหน้าจอของสคริปต์ใช้เฉพาะไฟล์บทบาท screens ที่แยกจริง ถ้าต้องมีรายละเอียดมากให้แยก screens ต่อท้าย
- ห้ามรวม source, decisions หรือ flows กับบทบาทอื่น เพื่อคงหลักฐาน การอ่านสถานะประเด็น และเลข Flow ให้ชัดเจน ทุกบทบาทแกนยังต้องอยู่ในทะเบียน
- เขียน source → scope/flows → decisions → delivery/แผน → README โดยเพิ่มประเด็นทันทีที่พบข้อเสนอ และใช้แม่แบบเฉพาะหัวข้อที่เกี่ยวข้อง
- ชุด standard ที่ส่งมอบแล้วไม่ยุบย้อนหลังเอง ชุด compact ที่โตขึ้นให้เพิ่มไฟล์ต่อท้ายและรักษาที่อยู่หัวข้อเดิม เมื่ออัปเกรด full ให้คง `document_style: compact` และไฟล์เดิม เพิ่ม architecture/data_model/api ต่อท้าย พร้อมปรับเนื้อหาและอ้างอิงให้ครบ full การรวมไฟล์ธุรกิจไม่ใช่เหตุให้ลดรายละเอียดเทคนิค
