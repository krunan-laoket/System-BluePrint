# การรีวิวและตรวจสอบความสอดคล้องของชุดเอกสาร

เป้าหมายของการรีวิวคือการตอบ **4 คำถามหลักด้วยหลักฐานที่ตรวจสอบได้จริง** ไม่ใช่ด้วยความรู้สึก:

1. **ถูกต้องตามต้นทางและบริบท** — เอกสารตรงกับสิ่งที่ลูกค้า/ผู้ใช้กำหนด แยกส่วนที่เป็นข้อเสนอของทีมออกอย่างชัดเจน และไม่ขัดต่อบริบทองค์กรหรือระเบียบหรือไม่?
2. **ใช้งานได้จริง** — ถ้าสร้างระบบตามเอกสารชุดนี้ ผู้ใช้แต่ละบทบาทจะทำงานของตัวเองตั้งแต่ต้นจนจบได้โดยไม่ติดทางตันหรือไม่?
3. **ไม่ขัดกันข้ามไฟล์** — ชื่อเรียก สถานะ สิทธิ์ ตัวเลข และโครงสร้างข้อมูลในทุกไฟล์พูดตรงกันทั้งหมดหรือไม่?
4. **ลำดับการทำงาน สถานะ และความเชื่อมโยงครบสมบูรณ์** — ทุกเส้นทางมีจุดเริ่ม จุดจบ ทางออกเมื่อเกิดกรณีผิดปกติ และสืบย้อนจากเป้าหมายไปถึงฟีเจอร์และเกณฑ์ตรวจรับได้ครบหรือไม่?

ผู้เขียนมักมองไม่เห็นช่องว่างของตัวเองเพราะสมองเติมสิ่งที่ขาดให้โดยอัตโนมัติ การรีวิวจึงต้องทำแบบ **เดินตามเอกสารทีละขั้นโดยใช้เฉพาะสิ่งที่เขียนไว้บนหน้ากระดาษ**

### รอบที่ 2: รีวิวเนื้อหาเชิงลึก 4 ด้าน

หากสภาพแวดล้อมสามารถเรียกผู้ช่วยย่อย (`subagent`) ได้ และชุดเอกสารมีขนาดกลางขึ้นไป (เกิน 800 บรรทัดรวมกัน) **แนะนำให้มอบหมายรอบนี้ให้ผู้ช่วยย่อยที่ไม่ได้ร่วมเขียน** โดยให้อ่านเฉพาะโฟลเดอร์เอกสาร ข้อมูลต้นทาง และไฟล์ `review.md` นี้ แล้วส่งตารางสิ่งที่พบกลับมา สายตาใหม่จะจับช่องว่างได้แม่นยำกว่าผู้เขียนเอง หากไม่ใช้ผู้ช่วยย่อย ให้เปิดอ่านไฟล์จริงใหม่ทุกไฟล์แล้วตรวจตามตารางนี้:

| ระดับความสำคัญ | ไฟล์และตำแหน่ง | สิ่งที่ตรวจพบ | วิธีแก้ไข |
|---|---|---|---|
| `ต้องแก้` / `ควรแก้` / `ข้อสังเกต` | | | |

- **`ต้องแก้`:** เอกสารผิดไปจากต้นทาง ขัดกันเองข้ามไฟล์ ตัวเลขไม่ตรงกัน หรือมีทางตันที่ทำให้ทำงานจบไม่ได้
- **`ควรแก้`:** ขาดรายละเอียดที่ทำให้นักพัฒนาต้องเดาเอง หรือใช้ศัพท์/รหัสที่คนทั่วไปอ่านไม่เข้าใจ
- **`ข้อสังเกต`:** เรื่องที่เป็นทางเลือกทางธุรกิจซึ่งต้องให้ผู้ใช้หรือลูกค้าตัดสินใจ (ให้นำไปเพิ่มในไฟล์ประเด็นตัดสินใจ)

#### ด้านที่ 1: ถูกต้องตามต้นทางและบริบทองค์กร

ตรวจสอบเทียบกับ `docs/00-source.md` และไฟล์ต้นทางของผู้ใช้:
1. **ไม่ตกหล่นจากต้นทาง:** ไล่ข้อกำหนดต้นทางทีละข้อ ทีละประโยค แล้วหาว่าอยู่ในไฟล์และหัวข้อใดของชุดเอกสาร หากข้อใดหาไม่เจอ แปลว่าเอกสารตกหล่น
2. **แยกข้อเสนอออกจากข้อกำหนดลูกค้าชัดเจน:** สิ่งที่เอกสารเขียนไว้แต่ต้นทางไม่ได้ระบุ ต้องมีเครื่องหมาย `(รอยืนยัน)` (หรือใช้การประกาศสลับฝั่งที่ต้นไฟล์ตามกฎใน `SKILL.md`) และตามไปถึงประเด็นในไฟล์ประเด็นตัดสินใจได้ครบถ้วน โดยเฉพาะใน `02-features.md` ซึ่งใช้เป็นขอบเขตข้อตกลงกับลูกค้า
3. **ตรงตามรูปแบบที่ลูกค้าบังคับ:** คอลัมน์ของรายงาน ชื่อขั้นตอน หรือรูปแบบรหัสที่ลูกค้ากำหนดตายตัว ต้องตรงตามตัวอักษร
4. **คำตอบที่ผู้ใช้ยืนยันระหว่างทาง:** ถูกนำไปอัปเดตครบทุกไฟล์ที่เกี่ยวข้อง ไม่ใช่แก้แค่ไฟล์เดียวแล้วไฟล์อื่นยังเป็นค่าเก่า
5. **ความถูกต้องตามบริบทไทย (`discovery-and-thai-context.md`):**
   - ข้อมูลส่วนบุคคลในระบบมีมาตรการรองรับในไฟล์ความปลอดภัย/PDPA ครบถ้วน
   - หากเป็นบริบทหน่วยงานราชการ/TOR: ตรวจสอบว่าไม่มีการระบุยี่ห้อหรือเทคโนโลยีเป็นการล็อกสเปกในส่วนข้อกำหนดความต้องการ เว้นแต่ระบุที่มาชัดเจนว่าเป็นข้อบังคับของระบบเดิม และมีหัวข้อการส่งมอบ การรับประกัน และ SLA ครบถ้วน

#### ด้านที่ 2: ใช้งานได้จริง (End-to-End Walkability)

จำลองตัวเองเป็นผู้ใช้จริงแต่ละบทบาท แล้วเดินตามเอกสารทีละขั้นอย่างน้อยในสถานการณ์เหล่านี้:
- เส้นทางหลักของผู้ใช้แต่ละกลุ่ม ตั้งแต่เข้าสู่ระบบครั้งแรกจนจบงาน
- เส้นทางที่มีการส่งต่องานหรือการอนุมัติระหว่างหลายบทบาทหรือหลายระบบ
- เส้นทางของผู้ดูแลระบบในการตั้งค่าและเตรียมข้อมูลตั้งต้นก่อนเปิดใช้งานวันแรก
- เส้นทางกรณีผิดปกติ 2–3 แบบที่มีโอกาสเกิดบ่อยที่สุด (เช่น ข้อมูลถูกตีกลับแก้ไข, รอเกินเวลา, ขอยกเลิก)

**ในแต่ละขั้นที่เดินตาม Flow ให้ถาม 5 คำถามนี้เสมอ:**
1. คนในขั้นนี้ **รู้ได้อย่างไรว่าถึงตาตัวเองต้องทำ** (มีการแจ้งเตือน หรือมีรายการค้างแสดงบนหน้าจอใด)?
2. **มีหน้าจอให้ทำขั้นนี้หรือไม่** และหน้าจอนั้นอยู่ในไฟล์รายการหน้าจอ (`screens.md`) หรือไม่?
3. หน้าจอนั้น **เรียก API ใด** API นั้นอยู่ใน `06-api-spec.md` หรือไม่ และบทบาทนี้มีสิทธิ์เรียกหรือไม่? (ข้ามข้อนี้หากเป็นโหมดขอบเขตธุรกิจ/TOR)
4. ข้อมูลที่ต้องกรอกหรือนำมาแสดง **มีฟิลด์ใน `05-data-model.md` หรือไม่** และข้อมูลนั้น **ถูกเก็บเข้ามาตั้งแต่ขั้นก่อนหน้าแล้วหรือยัง**?
5. เมื่อกดทำเสร็จแล้ว **เกิดอะไรขึ้นต่อ และใครรับช่วงต่อ**?

**ถามคำถามโลกความจริงเพิ่มเติม:**
- งานที่ต้องให้คนทำด้วยมือ มีใครรับผิดชอบ ทำบ่อยแค่ไหน และปริมาณงานจริงทำไหวหรือไม่?
- นอกเวลาทำการ วันหยุดราชการ หรือเมื่อผู้อนุมัติลา งานจะค้างอยู่ที่ใดและมีทางออกอย่างไร?
- ข้อมูลตั้งต้น (Seed Data) ที่ต้องมีก่อนเปิดใช้ มาจากไหนและใครเป็นคนนำเข้า?
- การแบ่งเฟสในไฟล์แผนพัฒนา ส่งมอบสิ่งที่ใช้งานได้จริงทีละเฟสหรือไม่ (มีเฟสต้นที่แอบพึ่งพาของที่อยู่ในเฟสหลังหรือไม่)?

#### ด้านที่ 3: ไม่ขัดกันข้ามไฟล์ (Cross-File Consistency)

ตรวจเทียบเป็นคู่ไฟล์ สิ่งเดียวกันต้องเขียนตรงกันทุกที่:

| สิ่งที่ตรวจเทียบ | ไฟล์ที่ต้องตรงกันทุกจุด |
|---|---|
| **ชื่อและจำนวนของบทบาท ประเภท ช่องทาง** | `01-overview.md` ↔ `02-features.md` ↔ `05-data-model.md` ↔ `screens.md` |
| **ชื่อสถานะ และเส้นทางการเปลี่ยนสถานะ** | `03-flows.md` (ทั้งข้อความ ตาราง และผัง Mermaid) ↔ `05-data-model.md` (`enum`) ↔ `06-api-spec.md` |
| **สิทธิ์ของแต่ละบทบาท** | `02-features.md` ↔ `06-api-spec.md` ↔ `screens.md` ↔ `security-pdpa.md` |
| **ตัวเลขค่าตั้งต้นของระบบ (เวลา เพดาน อัตรา จำนวนครั้ง)** | ทุกไฟล์ที่กล่าวถึงต้องอ้างอิงและตรงกับตาราง **"ค่าที่ตั้งได้ในระบบ"** ใน `03-flows.md` (หรือ `business-rules.md`) และมีคีย์ใน `05-data-model.md` |
| **Path และ Method ของ API** | `06-api-spec.md` ↔ `screens.md` ↔ `development-plan.md` |
| **ชื่อฟิลด์และชนิดข้อมูล** | `05-data-model.md` ↔ `06-api-spec.md` ↔ `migration.md` ↔ `reports.md` |
| **จำนวนสรุป (จำนวนหน้าจอ ประเด็น API Entity)** | ตารางสรุปในเอกสาร ↔ จำนวนที่ `scripts/check_docs.py` นับได้จริง |
| **ชื่องานตั้งเวลา (Scheduler) และรอบเวลา** | `03-flows.md` ↔ `06-api-spec.md` |
| **ฟีเจอร์ที่แยกไว้ทำ `(เฟสหลัง)`** | `02-features.md` ↔ `screens.md` ↔ `06-api-spec.md` ↔ `development-plan.md` |
| **ตัวเลขในตารางตัวอย่างและรายงาน** | บวกกันถูกต้องทุกแถว/คอลัมน์ และตรงกันเมื่อใช้ตัวอย่างเดียวกันข้ามตาราง |

**ตรวจการใช้คำศัพท์:** สิ่งเดียวกันต้องเรียกด้วยคำเดียวกันทั้งชุด (เช่น ไม่เรียก `"ลูกค้า"` ในไฟล์หนึ่งแล้วเปลี่ยนเป็น `"สมาชิก"` หรือ `"ผู้ซื้อ"` ในอีกไฟล์ หากหมายถึงคนกลุ่มเดียวกัน)

1. **สำหรับทุก Flow ใน `03-flows.md`:**
   - มีครบทั้ง เงื่อนไขก่อนเริ่ม, ขั้นตอน, ผลลัพธ์, และกรณีอื่น
   - ทุกทางแยก (`ถ้า...`) มีทางไปต่อครบทุกกรณี
   - ทุกจุดที่ต้องรอคนหรือระบบภายนอก บอกชัดเจนว่ารอนานเท่าไร ครบเวลาแล้วเกิดอะไรขึ้น และใครถูกแจ้งเตือน
   - ทุกการกระทำอัตโนมัติ บอกตัวกระตุ้น วิธีรับมือเมื่อล้มเหลว และผลลัพธ์เมื่อเกิดการกดซ้ำ/รันซ้ำ หรือมีคนทำพร้อมกันสองคน (Concurrency & Idempotency)
2. **สำหรับทุกสิ่งที่มีสถานะ (State Machine):**
   - ทุกสถานะมีทางเข้าอย่างน้อย 1 ทาง
   - ทุกสถานะที่ไม่ใช่สถานะสุดท้ายมีทางออกอย่างน้อย 1 ทาง (ไม่มีสถานะที่เข้าแล้วค้างตลอดไป)
   - สถานะสุดท้ายระบุชัดเจน และบอกว่าเปิดกลับมาแก้ไขใหม่ได้หรือไม่
   - **ตารางสถานะ ผังสถานะ (Mermaid) และคำอธิบายใน Flow บอกเส้นทางชุดเดียวกันทุกเส้น** (ไล่ตรวจทีละลูกศรในผังเทียบกับแถวในตาราง)
   - มีทางยกเลิกหรือถอยกลับสำหรับรายการที่ผู้ใช้ทำผิดพลาดได้
3. **ความเชื่อมโยงทั้งระบบ (System-wide Traceability):**
   - ทุกเป้าหมายใน `01-overview.md` มีฟีเจอร์ใน `02-features.md` หรือเป้าหมายด้านคุณภาพรองรับ
   - ทุกช่องทางที่งานเข้ามาได้ มี Flow รองรับตั้งแต่เข้าจนจบ
   - ทุกฟีเจอร์ใน `02-features.md` ปรากฏอยู่ใน `03-flows.md` อย่างน้อย 1 Flow หรือเป็นฟีเจอร์ตั้งค่าที่มีหน้าจอรองรับ
   - ทุกขั้นใน Flow มีฟีเจอร์รองรับ (ถ้า Flow พูดถึงความสามารถที่ยังไม่มีใน `02-features.md` ต้องเพิ่มเข้า `02-features.md`)
   - หากมีไฟล์ `acceptance.md` ตารางเมทริกซ์สอบกลับต้องโยงครบและไม่มีช่องโหว่ที่ถูกปล่อยว่างโดยไม่แจ้งเตือน

### รอบที่ 3: แก้ไขและรันสคริปต์ตรวจซ้ำ

1. แก้ไขทุกรายการระดับ `ต้องแก้` และ `ควรแก้` เมื่อแก้ที่ไฟล์หนึ่ง ต้องไล่แก้ไฟล์อื่นที่อ้างถึงเรื่องเดียวกันให้ตรงกันทั้งหมด (แนะนำให้ใช้ `scripts/replace_checked.py` เมื่อต้องเปลี่ยนคำหรือข้อความเดียวกันหลายไฟล์)
2. นำรายการระดับ `ข้อสังเกต` ที่ต้องรอให้ลูกค้าหรือผู้บริหารตัดสินใจ ไปต่อท้ายในไฟล์ประเด็นตัดสินใจ พร้อมอัปเดตตารางสรุปต้นไฟล์
3. รัน `scripts/check_docs.py` ซ้ำจนกว่าจะไม่มีรายการระดับ `ผิดพลาด`
4. หากมีการแก้ไขครั้งใหญ่ (รวมเกิน 10 รายการ หรือแก้เกิน 5 ไฟล์) ให้ตรวจทานด้านที่ 3 และด้านที่ 4 ซ้ำในไฟล์ที่ถูกแก้ไขอีกครั้งเพื่อป้องกันจุดขัดแย้งใหม่
5. อัปเดตสถานะเอกสารใน `README.md` ว่าผ่านการตรวจทานความสอดคล้องแล้วเมื่อวันที่เท่าใด

### รอบที่ 4: รายงานผู้ใช้ตามความจริง

ส่งสรุปผลการรีวิวให้ผู้ใช้ทราบ 4 หัวข้อสั้นๆ:
1. **สิ่งที่ตรวจแล้ว:** ผลการรันสคริปต์อัตโนมัติ การวาดผัง Mermaid และสถานการณ์ที่เดินตรวจทาน
2. **สิ่งที่พบและแก้ไขเรียบร้อยแล้ว:** จำนวนรายการที่แก้ไข พร้อมยกตัวอย่างจุดสำคัญ 3–5 เรื่องที่ช่วยอุดช่องโหว่ของระบบ
3. **ข้อจำกัดของการตรวจ:** สิ่งที่ต้องให้ผู้เชี่ยวชาญหรือเอกสารภายนอกยืนยัน เช่น ข้อจำกัดล่าสุดของ API ภายนอก หรือการตรวจสอบข้อกฎหมายโดยฝ่ายกฎหมาย
4. **ประเด็นที่ต้องตัดสินใจต่อ:** ชี้ไปที่ไฟล์ประเด็นตัดสินใจ โดยแยกประเด็นเร่งด่วนที่ **บล็อกการเริ่มพัฒนา** ออกมาให้เห็นชัดเจนเป็นอันดับแรก
