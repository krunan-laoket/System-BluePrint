# การรีวิวและตรวจสอบความสอดคล้องของชุดเอกสาร

เป้าหมายของการรีวิวคือการตอบ **4 คำถามหลักด้วยหลักฐานที่ตรวจสอบได้จริง** ไม่ใช่ด้วยความรู้สึก:

1. **ถูกต้องตามต้นทางและบริบท** — เอกสารตรงกับสิ่งที่ลูกค้า/ผู้ใช้กำหนด แยกส่วนที่เป็นข้อเสนอของทีมออกอย่างชัดเจน และไม่ขัดต่อบริบทองค์กรหรือระเบียบหรือไม่?
2. **ใช้งานได้จริง** — ถ้าสร้างระบบตามเอกสารชุดนี้ ผู้ใช้แต่ละบทบาทจะทำงานของตัวเองตั้งแต่ต้นจนจบได้โดยไม่ติดทางตันหรือไม่?
3. **ไม่ขัดกันข้ามไฟล์** — ชื่อเรียก สถานะ สิทธิ์ ตัวเลข และโครงสร้างข้อมูลในทุกไฟล์พูดตรงกันทั้งหมดหรือไม่?
4. **ลำดับการทำงาน สถานะ และความเชื่อมโยงครบสมบูรณ์** — ทุกเส้นทางมีจุดเริ่ม จุดจบ ทางออกเมื่อเกิดกรณีผิดปกติ และสืบย้อนจากเป้าหมายไปถึงฟีเจอร์และเกณฑ์ตรวจรับได้ครบหรือไม่?

ผู้เขียนมักมองไม่เห็นช่องว่างของตัวเองเพราะสมองเติมสิ่งที่ขาดให้โดยอัตโนมัติ การรีวิวจึงต้องทำแบบ **เดินตามเอกสารทีละขั้นโดยใช้เฉพาะสิ่งที่เขียนไว้บนหน้ากระดาษ**

ก่อนรีวิว อ่าน `mode` และ `documents` จาก `blueprint.json`:
- `{{role}}` ในไฟล์นี้คือ path จริงของบทบาทนั้น ในรายงานผลให้เขียน path จริง
- **ข้ามรายการตรวจที่อ้างบทบาทซึ่งโครงการไม่มี** เช่น business ไม่มี architecture, data_model, api จึงตรวจกลุ่มข้อมูล สิทธิ์ เงื่อนไข และผลทางธุรกิจใน overview/features/flows แทน full ที่เว้น API ไม่ต้องสร้าง API เพื่อผ่านรีวิว ระบบที่ไม่มีหน้าจอให้ตรวจจุดเรียกใช้งานหรือผลลัพธ์จริงแทนหน้าจอ
- อ่าน document_style ด้วย compact อาจมีหลายบทบาทในไฟล์เดียวตาม file-set.md หัวข้อ 5 ให้ตรวจแต่ละบทบาทครบแม้เปิดไฟล์ครั้งเดียว หน้าจอใน scope ตรวจด้วยเลขหัวข้อใน overview ไม่สร้าง screens เพื่อให้ครบรายการ จำนวนหน้าจอที่รวมอยู่ใน scope ต้องทวนด้วยการอ่าน

## ลำดับการรีวิว 4 รอบ

### รอบที่ 1: ตรวจด้วยสคริปต์อัตโนมัติ

รันสคริปต์ตรวจกลไกและความเชื่อมโยง:

```bash
python3 <โฟลเดอร์สกิล>/scripts/check_docs.py <โฟลเดอร์โครงการ>     # macOS/Linux
py -3 <โฟลเดอร์สกิล>\scripts\check_docs.py <โฟลเดอร์โครงการ>       # Windows (หรือ python)
```

หากเครื่องมีเบราว์เซอร์ Chrome หรือ Edge และเชื่อมต่ออินเทอร์เน็ตได้ ให้เพิ่ม `--render` ต่อท้ายคำสั่งเดียวกัน เพื่อให้สคริปต์ลองวาดผัง Mermaid ทุกผังจริง (ป้องกันผังผิดไวยากรณ์แล้วแสดงเป็นข้อความ Error ต่อหน้าลูกค้า) ถ้าไม่มีเบราว์เซอร์หรืออินเทอร์เน็ต สคริปต์จะแจ้งว่าข้ามการวาด ให้รายงานผังว่า "ไม่ได้ตรวจ"

การเอ่ยชื่อไฟล์เป็นข้อความใช้ได้ทั้งชื่อไฟล์ (`02-features.md`) และ path เต็มจากทะเบียน (`docs/02-features.md`) ตัวพิมพ์ต้องตรงกับไฟล์จริง ส่วนลิงก์ Markdown `[..](..)` ใช้ path สัมพัทธ์กับไฟล์ที่เขียนลิงก์

#### รูปแบบการอ้างอิงข้ามไฟล์ที่สคริปต์ตรวจได้แม่นยำ (ควรใช้รูปแบบเหล่านี้ตั้งแต่ตอนเขียน)
- **ชื่อไฟล์ ตามด้วยคำว่า `ข้อ` (หรือ `หัวข้อ`) และเลขหัวข้อ:** เช่น `{{api}} ข้อ 4`, `{{features}} ข้อ 1.2.3` หลายเลขเขียนได้ เช่น `ข้อ 1.1 และข้อ 2.3` หรือ `ข้อ 3, 4 และ 6` (ตรวจทุกเลข)
- **คำว่า `Flow` ตามด้วยเลข:** เช่น `Flow 5`
- **คำว่า `ประเด็นที่` ตามด้วยเลข:** เช่น `ประเด็นที่ 12` หรือ `ประเด็นที่ 3, 4 และ 5`
- ใช้เลขอารบิก (0–9) ในเลขหัวข้อ เลขข้อ และเลขประเด็น ตัวตรวจไม่นับเลขไทยเป็นเลขอ้างอิง
- รายการเลขต่อกันใช้ได้กับคำนำชนิดเดียวกัน ถ้าปนชนิด เช่น `Flow 2, ประเด็นที่ 11` ให้เขียนคำนำกำกับทุกเลข (ตัวตรวจแยกชนิดตามคำนำ)
- สิ่งที่ตัวตรวจไม่ตรวจ ต้องรีวิวด้วยตา: API path ในไฟล์หน้าจอมีในไฟล์ API จริงหรือไม่, ค่า enum ตรงกับตารางสถานะหรือไม่, และตัวเลขสรุปอื่นนอกจากจำนวนหน้าจอ
- **ชื่อไฟล์ `.md` ทุกชื่อที่ปรากฏ:** เช่น `plans/mockup-plan.md`

ท้ายผลการรัน สคริปต์จะพิมพ์ **"จำนวนที่นับได้จริง"** (จำนวน Flow, จำนวนประเด็นแยกตามสถานะ, จำนวนแถวหน้าจอ, จำนวนแถว API, จำนวน Entity, และจำนวนจุดที่ติดเครื่องหมายรอยืนยัน) ให้ผู้เขียนนำตัวเลขจริงนี้ไปเทียบกับตารางสรุปในเอกสารทุกครั้ง

**ต้องแก้ทุกรายการที่เป็น `ผิดพลาด` ให้เหลือ 0 และพิจารณารายการ `เตือน` ทีละข้อก่อนไปรอบที่ 2**

### รอบที่ 2: รีวิวเนื้อหาเชิงลึก 4 ด้าน

หากสภาพแวดล้อมสามารถเรียกผู้ช่วยย่อย (`subagent`) ได้ และชุดเอกสารมีขนาดกลางขึ้นไป (เกิน 800 บรรทัดรวมกัน) **แนะนำให้มอบหมายรอบนี้ให้ผู้ช่วยย่อยที่ไม่ได้ร่วมเขียน** โดยให้อ่านเฉพาะโฟลเดอร์เอกสาร ข้อมูลต้นทาง และไฟล์ `review.md` นี้ แล้วส่งตารางสิ่งที่พบกลับมา สายตาใหม่จะจับช่องว่างได้แม่นยำกว่าผู้เขียนเอง หากไม่ใช้ผู้ช่วยย่อย ให้เปิดอ่านไฟล์จริงใหม่ทุกไฟล์แล้วตรวจตามตารางนี้:

| ระดับความสำคัญ | ไฟล์และตำแหน่ง | สิ่งที่ตรวจพบ | วิธีแก้ไข |
|---|---|---|---|
| `ต้องแก้` / `ควรแก้` / `ข้อสังเกต` | | | |

- **`ต้องแก้`:** เอกสารผิดไปจากต้นทาง ขัดกันเองข้ามไฟล์ ตัวเลขไม่ตรงกัน หรือมีทางตันที่ทำให้ทำงานจบไม่ได้
- **`ควรแก้`:** ขาดรายละเอียดที่ทำให้นักพัฒนาต้องเดาเอง หรือใช้ศัพท์/รหัสที่คนทั่วไปอ่านไม่เข้าใจ
- **`ข้อสังเกต`:** เรื่องที่เป็นทางเลือกทางธุรกิจซึ่งต้องให้ผู้ใช้หรือลูกค้าตัดสินใจ (ให้นำไปเพิ่มในไฟล์ประเด็นตัดสินใจ)

#### ด้านที่ 1: ถูกต้องตามต้นทางและบริบทองค์กร

ตรวจสอบเทียบกับ `{{source}}` และไฟล์ต้นทางของผู้ใช้:
1. **ไม่ตกหล่นจากต้นทาง:** ไล่ข้อกำหนดต้นทางทีละข้อ ทีละประโยค แล้วหาว่าอยู่ในไฟล์และหัวข้อใดของชุดเอกสาร หากข้อใดหาไม่เจอ แปลว่าเอกสารตกหล่น
2. **แยกข้อเสนอออกจากข้อกำหนดลูกค้าชัดเจน:** สิ่งที่เอกสารเขียนไว้แต่ต้นทางไม่ได้ระบุ ต้องมีเครื่องหมาย `(รอยืนยัน)` รายข้อ หรือ `(ทั้งหมวดรอยืนยัน)` ที่หัวข้อหมวด และตามไปถึงประเด็นในไฟล์ประเด็นตัดสินใจได้ครบถ้วน โดยเฉพาะใน `{{features}}` ซึ่งใช้เป็นขอบเขตข้อตกลงกับลูกค้า
3. **ตรงตามรูปแบบที่ลูกค้าบังคับ:** คอลัมน์ของรายงาน ชื่อขั้นตอน หรือรูปแบบรหัสที่ลูกค้ากำหนดตายตัว ต้องตรงตามตัวอักษร
4. **คำตอบที่ผู้ใช้ยืนยันระหว่างทาง:** ถูกนำไปอัปเดตครบทุกไฟล์ที่เกี่ยวข้อง ไม่ใช่แก้แค่ไฟล์เดียวแล้วไฟล์อื่นยังเป็นค่าเก่า
   - แหล่งข้อมูลมีฉบับ/หน้า/สถานะร่างหรือรับรองเท่าที่ทราบหรือไม่ การได้รับเอกสารไม่ใช่การรับรองข้อกำหนด
   - ข้อขัดแย้งเก็บที่มาทั้งสองฝั่ง เหตุผลของค่าชั่วคราว ผู้ยืนยัน และผลกระทบหรือไม่
   - "ทำต่อได้" ไม่ถูกเปลี่ยนเป็นยืนยันทุกข้อ และข้อที่ตัดสินใจแล้วมีหลักฐานจากผู้มีอำนาจจริงหรือไม่
5. **ความถูกต้องตามบริบทไทย (`discovery-and-thai-context.md`):**
   - ข้อมูลส่วนบุคคลในระบบมีมาตรการรองรับครบ ในไฟล์ความปลอดภัย/PDPA หรือในหัวข้อของภาพรวมเมื่อข้อมูลไม่ซับซ้อน (ตามเกณฑ์ใน `file-set.md`)
   - หากเป็นบริบทหน่วยงานราชการ/TOR: ตรวจสอบว่าไม่มีการระบุยี่ห้อหรือเทคโนโลยีเป็นการล็อกสเปกในส่วนข้อกำหนดความต้องการ เว้นแต่ระบุที่มาชัดเจนว่าเป็นข้อบังคับของระบบเดิม และมีหัวข้อการส่งมอบ การรับประกัน และ SLA ครบถ้วน
6. **ไม่ลอกข้อเท็จจริงจากตัวอย่าง:** เหตุผลของการตัดขอบเขต บทบาท ช่องทาง ระเบียบองค์กร และค่าลองใหม่ต้องมีต้นทางหรือเป็นข้อเสนอรอยืนยัน การที่ตัวอย่างใช้ค่านั้นไม่ใช่หลักฐานของโครงการนี้

#### ด้านที่ 2: ใช้งานได้จริง (End-to-End Walkability)

จำลองตัวเองเป็นผู้ใช้จริงแต่ละบทบาท แล้วเดินตามเอกสารทีละขั้นอย่างน้อยในสถานการณ์เหล่านี้:
- เส้นทางหลักของผู้ใช้แต่ละกลุ่ม ตั้งแต่เข้าสู่ระบบครั้งแรกจนจบงาน
- เส้นทางที่มีการส่งต่องานหรือการอนุมัติระหว่างหลายบทบาทหรือหลายระบบ
- เส้นทางของผู้ดูแลระบบในการตั้งค่าและเตรียมข้อมูลตั้งต้นก่อนเปิดใช้งานวันแรก
- เส้นทางกรณีผิดปกติ 2–3 แบบที่มีโอกาสเกิดบ่อยที่สุด (เช่น ข้อมูลถูกตีกลับแก้ไข, รอเกินเวลา, ขอยกเลิก)

**ในแต่ละขั้นที่เดินตาม Flow ให้ถาม 5 คำถามนี้เสมอ:**
1. คนในขั้นนี้ **รู้ได้อย่างไรว่าถึงตาตัวเองต้องทำ** (มีการแจ้งเตือน หรือมีรายการค้างแสดงบนหน้าจอใด)?
2. **มีหน้าจอให้ทำขั้นนี้หรือไม่** และหน้าจอนั้นอยู่ในไฟล์รายการหน้าจอ (`{{screens}}`) หรือไม่?
3. full ที่มี API: หน้าจอ/ผู้เรียกใช้สัญญาใดในไฟล์บทบาท api และมีสิทธิ์หรือไม่? business หรือ full ไม่มี API: ตรวจการกระทำ ผู้รับผิดชอบ และสิทธิ์ทางธุรกิจแทน
4. ข้อมูลที่ใช้ **มีแหล่งที่มาและถูกเก็บ/รับเข้ามาก่อนแล้วหรือยัง**? business เทียบกลุ่มข้อมูลใน overview; full เทียบรายละเอียดใน data_model ตามทะเบียน ไม่บังคับ schema กับ business
5. เมื่อกดทำเสร็จแล้ว **เกิดอะไรขึ้นต่อ และใครรับช่วงต่อ**?

**ถามคำถามโลกความจริงเพิ่มเติม:**
- งานที่ต้องให้คนทำด้วยมือ มีใครรับผิดชอบ ทำบ่อยแค่ไหน และปริมาณงานจริงทำไหวหรือไม่?
- นอกเวลาทำการ วันหยุดราชการ หรือเมื่อผู้อนุมัติลา งานจะค้างอยู่ที่ใดและมีทางออกอย่างไร?
- ข้อมูลตั้งต้น (Seed Data) ที่ต้องมีก่อนเปิดใช้ มาจากไหนและใครเป็นคนนำเข้า?
- การแบ่งเฟสในไฟล์แผนพัฒนา ส่งมอบสิ่งที่ใช้งานได้จริงทีละเฟสหรือไม่ (มีเฟสต้นที่แอบพึ่งพาของที่อยู่ในเฟสหลังหรือไม่)?

#### ด้านที่ 3: ไม่ขัดกันข้ามไฟล์ (Cross-File Consistency)

ตรวจเทียบเป็นคู่ไฟล์ สิ่งเดียวกันต้องเขียนตรงกันทุกที่:

ใช้เฉพาะบทบาทที่มีจริงตามโหมด บทบาทเทคนิคที่ไม่มีใน business ให้แทนการตรวจด้วยข้อกำหนดใน overview/features/flows ไม่เพิ่มไฟล์เทคนิค full ที่ไม่มี API ข้ามคู่ API ตามเหตุผลในทะเบียน

| สิ่งที่ตรวจเทียบ | ไฟล์ที่ต้องตรงกันทุกจุด |
|---|---|
| **ชื่อและจำนวนของบทบาท ประเภท ช่องทาง** | `{{overview}}` ↔ `{{features}}` ↔ `{{data_model}}` ↔ `{{screens}}` |
| **ชื่อสถานะ และเส้นทางการเปลี่ยนสถานะ** | `{{flows}}` (ทั้งข้อความ ตาราง และผัง Mermaid) ↔ `{{data_model}}` (`enum`) ↔ `{{api}}` |
| **สิทธิ์ของแต่ละบทบาท** | `{{features}}` ↔ `{{api}}` ↔ `{{screens}}` ↔ `{{security}}` |
| **ตัวเลขค่าตั้งต้นของระบบ (เวลา เพดาน อัตรา จำนวนครั้ง)** | ตรงกับตารางค่าหลักใน flows หรือกติกาธุรกิจ; full ตรวจวิธีอ่าน/เก็บค่าตาม data_model หรือ architecture ไม่บังคับ Entity ตั้งค่า |
| **Path และ Method ของ API** | `{{api}}` ↔ `{{screens}}` ↔ `{{development_plan}}` |
| **ชื่อฟิลด์และชนิดข้อมูล** | `{{data_model}}` ↔ `{{api}}` ↔ `{{migration}}` ↔ `{{reports}}` |
| **จำนวนสรุป (จำนวนหน้าจอ ประเด็น API Entity)** | ตารางสรุปในเอกสาร ↔ จำนวนที่ `scripts/check_docs.py` นับได้จริง |
| **ชื่องานตั้งเวลา (Scheduler) และรอบเวลา** | `{{flows}}` ↔ `{{api}}` |
| **ฟีเจอร์ที่แยกไว้ทำ `(เฟสหลัง)`** | `{{features}}` ↔ `{{screens}}` ↔ `{{api}}` ↔ `{{development_plan}}` |
| **ตัวเลขในตารางตัวอย่างและรายงาน** | บวกกันถูกต้องทุกแถว/คอลัมน์ และตรงกันเมื่อใช้ตัวอย่างเดียวกันข้ามตาราง |

**ตรวจการใช้คำศัพท์:** สิ่งเดียวกันต้องเรียกด้วยคำเดียวกันทั้งชุด (เช่น ไม่เรียก `"ลูกค้า"` ในไฟล์หนึ่งแล้วเปลี่ยนเป็น `"สมาชิก"` หรือ `"ผู้ซื้อ"` ในอีกไฟล์ หากหมายถึงคนกลุ่มเดียวกัน)

**ขั้นต่ำทางเทคนิคของ full:** เปิดรายละเอียดของทุก API/operation/message เทียบแม่แบบหัวข้อ 7 ต้องมีแบบข้อมูลเข้าออกที่ครบ เงื่อนไขตรวจสอบ ตัวอย่างผลสำเร็จ/ผิดพลาด และสิทธิ์ระดับรายการ คำสั่งเปลี่ยนข้อมูลต้องอธิบายผลเมื่อเรียกซ้ำหรือทำพร้อมกัน รายการจำนวนมากต้องมีขอบเขตการอ่าน/แบ่งหน้าเมื่อเกี่ยวข้อง เทียบกับข้อจำกัดใน data_model และวิธีรับมือความขัดข้องใน architecture ข้อที่ยังเป็นประเด็นให้บอกส่วนที่ยังพัฒนาหรือตรวจรับไม่ได้ ตารางชื่อ API และการผ่านสคริปต์ยังพิสูจน์ความครบของสัญญาไม่ได้

#### ด้านที่ 4: ลำดับการทำงาน สถานะ และความเชื่อมโยงครบสมบูรณ์

1. **สำหรับทุก Flow ใน `{{flows}}`:**
   - มีครบทั้ง เงื่อนไขก่อนเริ่ม, ขั้นตอน, ผลลัพธ์, และกรณีอื่น
   - ทุกทางแยก (`ถ้า...`) มีทางไปต่อครบทุกกรณี
   - ทุกจุดที่ต้องรอคนหรือระบบภายนอก บอกชัดเจนว่ารอนานเท่าไร ครบเวลาแล้วเกิดอะไรขึ้น และใครถูกแจ้งเตือน
   - ทุกการกระทำอัตโนมัติ บอกตัวกระตุ้น วิธีรับมือเมื่อล้มเหลว และผลลัพธ์เมื่อเกิดการกดซ้ำ/รันซ้ำ หรือมีคนทำพร้อมกันสองคน (Concurrency & Idempotency)
2. **สำหรับทุกสิ่งที่มีสถานะ (State Machine):**
   - ทุกสถานะมีทางเข้าอย่างน้อย 1 ทาง
   - ทุกสถานะที่ไม่ใช่สถานะสุดท้ายมีทางออกอย่างน้อย 1 ทาง (ไม่มีสถานะที่เข้าแล้วค้างตลอดไป)
   - สถานะสุดท้ายระบุชัดเจน และบอกว่าเปิดกลับมาแก้ไขใหม่ได้หรือไม่
   - **ตารางสถานะ ผังสถานะ (Mermaid) และคำอธิบายใน Flow บอกเส้นทางชุดเดียวกันทุกเส้น** (ไล่ตรวจทีละลูกศรในผังเทียบกับแถวในตาราง)
   - มีทางยกเลิกหรือถอยกลับสำหรับรายการที่ผู้ใช้ทำผิดพลาดได้
3. **ความเชื่อมโยงทั้งระบบ (System-wide Traceability):**
   - ทุกเป้าหมายใน `{{overview}}` มีฟีเจอร์ใน `{{features}}` หรือเป้าหมายด้านคุณภาพรองรับ
   - ทุกช่องทางที่งานเข้ามาได้ มี Flow รองรับตั้งแต่เข้าจนจบ
   - ทุกฟีเจอร์ใน `{{features}}` ปรากฏอยู่ใน `{{flows}}` อย่างน้อย 1 Flow หรือเป็นฟีเจอร์ตั้งค่าที่มีหน้าจอรองรับ
   - ทุกขั้นใน Flow มีฟีเจอร์รองรับ (ถ้า Flow พูดถึงความสามารถที่ยังไม่มีใน `{{features}}` ต้องเพิ่มเข้า `{{features}}`)
   - มีบทบาท acceptance ทุกโครงการ ฟีเจอร์ คุณภาพ และสิ่งส่งมอบมีวิธีตรวจรับ/หลักฐาน ตารางสอบกลับต้องโยงครบหรือแสดงช่องว่างเป็นประเด็น ไม่บังคับให้ข้อกำหนดคุณภาพทุกข้อมีหน้าจอหรือ Flow ของผู้ใช้

### รอบที่ 3: แก้ไขและรันสคริปต์ตรวจซ้ำ

1. แก้ไขทุกรายการระดับ `ต้องแก้` และ `ควรแก้` เมื่อแก้ที่ไฟล์หนึ่ง ต้องไล่แก้ไฟล์อื่นที่อ้างถึงเรื่องเดียวกันให้ตรงกันทั้งหมด (แนะนำให้ใช้ `scripts/replace_checked.py` เมื่อต้องเปลี่ยนคำหรือข้อความเดียวกันหลายไฟล์)
2. นำรายการระดับ `ข้อสังเกต` ที่ต้องรอให้ลูกค้าหรือผู้บริหารตัดสินใจ ไปต่อท้ายในไฟล์ประเด็นตัดสินใจ พร้อมอัปเดตตารางสรุปต้นไฟล์
3. รัน `scripts/check_docs.py` ซ้ำจนกว่าจะไม่มีรายการระดับ `ผิดพลาด`
4. ตรวจซ้ำตามผลกระทบ โดยเฉพาะเมื่อเปลี่ยนขอบเขต สิทธิ์ สถานะ กฎคำนวณ สัญญาข้อมูล หรืออัปเกรดโหมด แม้เปลี่ยนเพียงข้อเดียว ไม่ใช้จำนวนไฟล์เป็นตัวตัดสินเพียงอย่างเดียว
5. อัปเดตสถานะเอกสารใน `README.md` ว่าผ่านการตรวจทานความสอดคล้องแล้วเมื่อวันที่เท่าใด
